# Публикация разбора Architecture

Репозиторий: `architecture-lab`, карта — `architecture-map.md`, разборы — `q/`.
Доска — `Architecture Mobile Knowledge` (`gh project` номер 9, владелец берётся
из `gh repo view`). Канал — `Architecture Knowledge`, отдельный от остальных.

Отличие от kotlin-lab: **CI-стендов здесь нет**. Архитектурное решение
проверяется тем, как оно ведёт себя на длинной дистанции, а не прогоном за
минуту в Actions, поэтому доказательство — приложенный артефакт (свой код,
разбор чужого, ADR), а не зелёный `check.sh`. Гейт проверяет только, что
артефакт приложен и лежит на месте; читает его человек.

## Статусы на доске и ворота

Цепочка статусов одна на все пять областей знаний, описана в
`pool-digest/scripts/workflow.py`. Статус называет работу, которая идёт
**сейчас**, поэтому ворота проверяются на выходе из него:

| Статус | Что делается | Чтобы уйти дальше |
|---|---|---|
| `Map` | ничего, пункт карты не выбран | — |
| `Todo` | ждёт в пуле | — |
| `Pre-analysis` | пишется предразбор | комментарий с заголовком `## Предразбор` (его пишет скилл issue-pre-analysis) |
| `In Analysis` | пишется `q/<slug>.md` | файл с якорем `Issue: [#N]`, доказательство приложено |
| `Telegraph Page` | разбор заливается страницей | запись о файле в `telegraph.json` |
| `Telegram Post` | пишется и уходит пост | комментарий с маркером `<!-- post: message_id=N -->` |
| `Done` | закрыто | — |

Сторож в `pool-digest` ходит по доскам раз в час и откатывает карточку, которая
уехала вперёд без артефакта, с комментарием — что именно не найдено. Двигать
статус руками мимо ворот бесполезно: следующий проход вернёт назад.

Из этого следуют два правила для этого скилла:

- **не начинай разбор, если в issue нет комментария-предразбора.** Скажи об этом
  и предложи сначала прогнать `issue-pre-analysis`. Предразбор — это граница
  вопроса: что входит, что сознательно не входит, какая документация читается.
- **маркеры ставит скилл, а не человек.** После публикации поста комментарий с
  `message_id` обязателен: без него ворота считают, что пост не вышел, и
  откатывают карточку из `Telegram Post`.

Номер доски, путь карты и модель доказательства для этого репозитория лежат в
`.claude/area.json` — бери их оттуда, а не из памяти.

## Шаг 1. Сплит issue на карточки

Нужен, когда в одной issue склеено несколько вопросов («как работает X и почему
тормозит на Y и что с этим в CMP»). Признак: в разборе получается два-три
независимых ответа, которые ссылаются друг на друга, а не один связный.

Не разбивай молча. Сначала покажи предлагаемое деление списком в одну строку на
вопрос и дождись «да».

После подтверждения:

1. **Карта.** Заменить строку в `architecture-map.md` на N строк, сохранив пометки
   (`[ ]`, `[~]`, `[!]`) и раздел. Формулировка каждой строки — самостоятельный
   вопрос, а не обрубок исходного.
2. **Issue.** Тело issue в этом репозитории — сама формулировка вопроса, одной
   строкой, без шапки с полями: раздел живёт в `topic` на доске.

   ```bash
   gh issue create --title "<вопрос>" --body "<вопрос>"
   ```

   Лейблов версии здесь нет и заводить их не надо: архитектурное решение не
   привязано к релизу библиотеки — оно живёт дольше любого из них.
3. **Привязка к разделу.** Каждая новая issue — sub-issue родительской issue
   раздела (`#1`–`#7`), иначе выпадет из счётчика прогресса:

   ```bash
   gh api -X POST repos/{owner}/{repo}/issues/<PARENT>/sub_issues -f sub_issue_id=<ID>
   ```

   `<ID>` — числовой `id` из REST API, а не номер issue и **не** node-id из
   `gh issue view --json id`: с node-id эндпоинт отвечает `422 Invalid property
   /sub_issue_id: not of type integer`. Брать так:

   ```bash
   gh api repos/{owner}/{repo}/issues/<N> -q .id
   ```
4. **Доска.** Добавить в проект и выставить поля `Status` = `Todo` (или тот статус
   цепочки, на котором разбор реально стоит), `topic` — раздел (`Состояние и
   поток данных`, `Слои и границы`, `Зависимости и время жизни`, `Данные:
   источник истины и синхронизация`, `Навигация и время жизни экранов`,
   `Модуляризация`, `Эволюция и деградация`), `needs code` = `yes` для пунктов с `[!]`:

   ```bash
   gh project item-add 9 --owner <owner> --url <issue-url>
   ```
5. **Исходную issue** закрыть как разбитую, со ссылками на новые:
   `gh issue close <N> --comment "Разбито на #A, #B, #C"`. Если разбор по ней уже
   написан — не закрывать здесь, она закроется коммитом на шаге 2.

Файлы разборов — по файлу на вопрос, `q/<slug>.md`. Артефакты доказательства и
песочница — рядом, в `q/<slug>/`; несколько разборов могут ссылаться на одну
песочницу, если она общая по смыслу. В шапке каждого файла — навигация на два
соседних вопроса и на раздел карты.

## Шаг 2. Доказательство

У каждого разбора в шапке — строка `**Доказано:**`, а под ней ссылки на файлы в
`q/<slug>/`. Что здесь считается доказательством:

| Вопрос про | Чем доказывается |
|---|---|
| форму состояния, границы слоёв | минимальный код в `q/<slug>/`, где решение и его альтернатива стоят рядом |
| время жизни, скоупы зависимостей | граф зависимостей или лог создания/уничтожения, приложенный файлом |
| синхронизацию и источник истины | сценарий расхождения: код или последовательность шагов, на которых оно воспроизводится |
| модуляризацию | граф модулей или замер времени сборки до и после |
| деградацию и эволюцию | разбор на живом коде — своём или чужом, со ссылкой на коммит |
| решение, принятое осознанно | ADR в `q/<slug>/`: контекст, варианты, выбор и предпосылки, которые можно перепроверить |

Разбор, который доказать нечем, пишется так и не прячется:

```markdown
**Доказано:** нечем — рассуждение без стенда
```

Он проходит гейт, но пометка остаётся видной. Не выдумывай доказательство, если
его нет, и не переписывай `**Доказано:**` под то, что удобно постить.

Перед коммитом прогнать проверку и вывести результат целиком:

```bash
python3 tools/check-evidence.py
```

**Красная проверка — стоп.** Она падает только на двух вещах: нет строки
`**Доказано:**` или файл, на который она ссылается, не лежит в репозитории.
Первое чинится текстом, второе — коммитом артефакта, а не удалением ссылки.

## Шаг 3. Коммит и пуш

1. Проверить, что артефакты сборки не попадают в индекс (`build/`, `.gradle/`
   должны быть в `.gitignore`) — `git status --short` перед `git add`. Трейсы и
   скрины доказательства коммитятся, сборка — нет.
2. Коммит. Сообщение на русском, в стиле репозитория: первая строка — что за
   разбор, дальше абзац о содержании, отдельной строкой — чем доказано, в конце
   `Closes #N` (несколько issue — несколько строк `Closes`).
3. Пуш: `git push`. **Пушить обязательно** — до пуша `Closes` не срабатывает,
   issue висит открытой, а ссылки в посте дают 404.
4. Проверить, что issue действительно закрылась: `gh issue view <N> --json state`.

Карту при закрытии не трогай: `architecture-map.md` между разметками не правится,
рабочее состояние живёт на доске. Статус в карте меняется только если
пользователь прямо просит.

## Шаг 4. Страницы в Telegra.ph

Репозиторий приватный, поэтому ссылки на GitHub в канале дадут 404. Текст
разборов публикуется в Telegra.ph — он открывается внутри Телеграма нативно.

```bash
# кнопкой из Actions: токен в секретах, telegraph.json коммитится сам
gh workflow run publish.yml -f files="q/<slug>*.md"

# локально, если токен есть в окружении
TELEGRAPH_TOKEN=... python3 tools/md-to-telegraph.py q/<slug>*.md
```

Аккаунт Telegra.ph у репозитория свой: `short_name` — `architecture-lab`, автор
страниц — `Architecture Knowledge` (константа `AUTHOR` в
`tools/md-to-telegraph.py`). Токена ещё нет: `telegraph.json` пуст, а секрет
`TELEGRAPH_TOKEN` в репозитории не заведён. Первую заливку делает пользователь —
`bash tools/telegraph-token.sh`, — и он же кладёт значение в секрет.

**Токен не заводится заново.** `tools/telegraph-token.sh` нужен один раз и
падает, если локальный файл уже есть: новый аккаунт сделает все прежние
страницы нередактируемыми навсегда. Если токен всё-таки потерян — заводить
новый должен пользователь, не ты.

Соответствие «файл → страница» лежит в `telegraph.json` этого репозитория и
коммитится. Адрес страницы при повторной заливке не меняется, старые посты в
канале не протухают. Прогон в два прохода — сначала создаются недостающие
страницы, потом все перезаливаются с проставленными ссылками друг на друга.

Что теряется при конвертации (Telegra.ph понимает узкий набор тегов):

- таблицы — разворачиваются в список, проверь, что читается
- ссылки на файлы кода и на карту становятся жирным текстом: вести в приватную
  репу некуда. Если код важен для понимания — вставь его в разбор блоком
- **картинки не переносятся**: скрин Layout Inspector или трейс останутся в
  репозитории и в канал не попадут. Если доказательство визуальное, перескажи
  его в разборе цифрами («было 47 рекомпозиций, стало 3»), иначе читатель
  канала увидит утверждение без опоры
- заголовки едут на уровень ниже: `##` → `h3`, `###` → `h4`

После заливки открой хотя бы одну страницу и посмотри глазами. Ссылки для поста
берутся из `telegraph.json`, а не из GitHub.

## Шаг 5. Пост в канал

Формат поста — короткий, по два-три предложения на вопрос:

```
🏗️ <b>Заголовок темы</b>

<b>1.</b> <a href="URL">Название вопроса</a>
Суть в двух предложениях: что происходит, где ломается.

<b>2.</b> <a href="URL">Название вопроса</a>
...

💊 Лекарство / вывод — одной строкой, при желании с <code>кодом</code>

#architecture #state
```

Правила:

- разметка только HTML (`<b>`, `<a href>`, `<code>`) — руками из клиента теги не
  парсятся, поэтому отправка идёт ботом
- ссылки — на страницы Telegra.ph из `telegraph.json`, по одной на вопрос
- никаких голых URL в тексте: ссылка вешается на название вопроса
- без вводного абзаца «сегодня разобрал» — сразу пункты
- эмодзи: одна в заголовке, одна на выводе, больше не надо
- в конце — контекст, если вывод от него зависит: размер команды, возраст
  кодовой базы, платформа. Архитектурное решение без контекста читается как
  универсальный совет, а универсальных здесь нет
- теги: `#architecture` плюс раздел (`#state`, `#layers`, `#di`, `#data`,
  `#navigation`, `#modules`, `#evolution`)

### Цитаты и длинный вывод

Telegram понимает `<blockquote>` и `<blockquote expandable>` — второй сворачивается
под «Показать полностью». Это решает главную проблему постов из этого
репозитория: замер доказывает утверждение, но картинку из Layout Inspector в канал
не отправить, а отчёт компилятора без разворачивания забивает весь пост.

```html
<blockquote expandable>restartable skippable fun ItemRow(item: Item)
  stable item: Item
unstable class Item { unstable val tags: List&lt;String&gt; }</blockquote>
```

Правила: цитата не вкладывается в цитату, внутри работает только инлайн-разметка
(`<b>`, `<code>`, `<a>`), а блок кода целиком — нет. Сворачиваемую цитату стоит
брать от четырёх строк: на двух Telegram не покажет кнопку, прятать нечего.
Лимит поста прежний — 4096 символов, свёрнутый текст считается полностью.

Не подменяй цитатой вывод в разборе: в посте — 10–15 строк, на которых держится вывод, полный вывод остаётся
файлом в `q/<slug>/` и пересказывается на странице Telegra.ph.

Текст поста кладётся в `posts/<тема>.html` и коммитится: воркфлоу берёт файл
из репозитория, а не с локального диска.

Два способа отправки — оба зовут один и тот же `post.sh`:

```bash
# локально, нужны TELEGRAM_BOT_TOKEN и TELEGRAM_CHANNEL в окружении
.claude/skills/q-publish/post.sh posts/latest.html

# кнопкой из Actions, секреты уже в репозитории
gh workflow run publish.yml -f post=posts/latest.html
```

Через Actions отправка не пройдёт, если проверка доказательств красная: джоба
поста зависит от неё. Заливку и пост можно сделать одним запуском —
`-f files="q/тема-*.md" -f post=posts/тема.html`, — но только когда адреса
страниц уже известны: текст поста пишется руками по готовым ссылкам.

### Превью перед отправкой

Пост в канал необратим, а увидеть его раньше было негде. Перед отправкой —
всегда прогон превью, оно же проверка:

```bash
python3 tools/post-preview.py posts/<тема>.html --open
```

Скрипт рисует пузырь в стилистике Telegram (светлая и тёмная тема, счётчик
символов) в `posts/preview.html` и падает на том, на чём Telegram молча портит
текст или отвечает `can't parse entities`: тег вне списка Bot API, незакрытый
или перекрещенный тег, длина сверх лимита, голый URL в тексте, ссылка на
`telegra.ph`, которой нет в `telegraph.json`. **Красное превью — стоп**,
отправлять нельзя. `posts/preview.html` в git не коммитится.

**Перед отправкой всегда показывай итоговый текст и спрашивай подтверждение.**
Пост в канал необратим: правится через `editMessageText`, удаляется руками.
После отправки запиши `message_id` из вывода — правка идёт по нему, новой
публикации быть не должно:

```bash
gh workflow run publish.yml -f post=posts/latest.html -f message_id=<id>
```

### Маркер публикации в issue

Сразу после отправки — комментарий в issue с маркером, по которому ворота
видят, что пост вышел:

```bash
gh issue comment <N> --body '<!-- post: message_id=42 -->
Опубликовано в канале: https://t.me/c/<id без -100>/42'
```

Без этого комментария сторож в `pool-digest` считает, что публикации не было,
и на ближайшем проходе откатит карточку из `Telegram Post` назад. Маркер —
скрытый HTML-комментарий: в интерфейсе GitHub он не виден.

### Обратная ссылка в issue

После публикации оставь комментарий в закрытой issue: список вопросов со
ссылками на страницы Telegra.ph, ссылка на пост в канале и напоминание, чем
разбор доказан. Иначе через полгода issue найдётся поиском, а текст к ней —
нет.

```bash
gh issue comment <N> --body-file <файл>
```

Ссылка на пост приватного канала строится как `https://t.me/c/<id без -100>/<message_id>`.
Открывается только у подписчиков канала.

### Секреты и адресат

Бот — общий с kotlin-lab и android-lab, различается только `TELEGRAM_CHANNEL`:
в секретах этого репозитория должен лежать id канала **Architecture Knowledge**.
Перепутанный id — единственный способ отправить разбор Architecture в чужой канал,
и `post.sh` этого не поймает: он проверяет тип адресата, а не какой именно канал.

`post.sh` до отправки зовёт `getChat` и отказывается писать куда-либо, кроме
канала. Если он ругается — причина в секретах, а не в тексте:

| Что говорит | Что чинить |
|---|---|
| `TELEGRAM_BOT_TOKEN не похож на токен` | значение пустое или без `<id>:<секрет>` |
| `Not Found` | токен пуст или в нём кавычки/префикс `bot` |
| `Unauthorized` | токен отозван или с опечаткой |
| `адресат не канал, а private` | в `TELEGRAM_CHANNEL` адрес бота, а не канала |
| `chat not found` | неверный id канала либо бот не админ |

Признак канала: id **отрицательный, с префиксом `-100`**, положительное число —
всегда пользователь или бот. Надёжный способ добыть id — написать что-нибудь в
канал и спросить у бота (он админ, значит видит посты канала):

```bash
curl -s "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/getUpdates" \
  | python3 -c "import json,sys; [print(u['channel_post']['chat']) for u in json.load(sys.stdin)['result'] if 'channel_post' in u]"
```

Запись секретов — обязательно `printf` (не `echo`: перевод строки уедет в URL)
и с явным репозиторием, иначе `gh` возьмёт репу из текущей директории:

```bash
printf '%s' '<значение>' | gh secret set TELEGRAM_CHANNEL -R <owner>/architecture-lab
```

Проверить, что запись доехала: `gh secret list -R <owner>/architecture-lab` — у
секрета должна стоять свежая дата. Значения не видны никому, включая тебя,
поэтому единственный способ проверить содержимое — прогон.

## Чего не делать

- не коммитить с красным `check-evidence.py`
- не выдумывать доказательство и не переписывать `**Доказано:**` под пост:
  «нечем» — допустимый и честный ответ
- не постить в канал, пока страницы не залиты в Telegra.ph: ссылки будут битые
