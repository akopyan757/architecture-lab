# производные состояния: вычислять vs хранить

Issue: [#19](https://github.com/akopyan757/architecture-lab/issues/19) · раздел: [1. Состояние и поток данных](../architecture-map.md)

**Доказано:** стенд в [`q/derived-state/`](derived-state/) — три версии одного
состояния корзины одним файлом ([`derived.kt`](derived-state/derived.kt)), запуск
([`run.sh`](derived-state/run.sh)), вывод ([`output.md`](derived-state/output.md))
и ADR ([`adr.md`](derived-state/adr.md)). Kotlin 2.4.20, зависимостей нет. Стенд
подтверждает утверждения текста, но сам текст от него не зависит.

## Коротко

Поле, которое прямо сейчас и всегда одинаково получается из соседних полей,
не хранят, а вычисляют геттером. Если вычисление дорого и читается много чаще,
чем меняется источник, его хранят только как кэш с ключом из всех входов.
Поле без ключа — второй источник истины, и оно разойдётся на первом же
писателе, который про него не знает.

## Три вопроса к полю

Перед тобой поле в state. Задай три вопроса по очереди: можно ли получить его
из других полей прямо сейчас; дорого ли это; и если дорого, как хранить, чтобы
хранимое не разошлось с источником. Ответ «хранить обычным полем» возможен
только на первом вопросе. Дальше выбор идёт между геттером и кэшем с ключом.

## Вопрос 1: получается ли значение из других полей прямо сейчас

Проверка: беру соседние поля state, считаю, получаю это значение. Повторяю
через час, получаю то же самое.

```kotlin
val totalPrice: Int          // items сложить — да, и всегда одинаково
val priceAtCheckout: Int     // сумма на момент оплаты; items с тех пор изменились — нет
val orderNumber: String      // случайный номер; два вызова дадут два номера — нет
val isOnline: Boolean        // ответ знает система, а не state — нет
```

Если «нет», это не производное поле, а самостоятельный факт: снимок на момент,
результат случайности, ответ другого процесса. Его хранят, и это не нарушение
единого источника истины — для своего факта оно и есть источник. Такое поле
хранится один раз, на границе с тем, кто его породил: `isOnline` живёт как
`StateFlow` из `callbackFlow`, а в state экрана входит через `combine`, не
копируется полем со своей мутацией.

Если «да», идём дальше.

## Вопрос 2: дорого ли считать

Дёшево — это сложение, склейка строк, сравнение, фильтр по десяткам элементов.
Тогда геттер и ничего больше:

```kotlin
data class CartState(val items: List<CartItem>) {
    val totalPrice get() = items.sumOf { it.price * it.qty }
    val isEmpty get() = items.isEmpty()
}
```

Поля в конструкторе нет, и испортить его некому. Сумма двадцати позиций на три
чтения в кадр — шестьдесят сложений; обсуждать тут нечего.

Дорого — это сортировка и фильтр по тысячам элементов, регулярные выражения,
декодирование картинки. И при этом читают много чаще, чем меняется источник:
список в пять тысяч строк перерисовывается на каждый кадр скролла, а обновляется
раз в минуту. Тогда третий вопрос.

## Вопрос 3: как хранить, чтобы не разошлось

Хранить только вместе с ключом. Ключ перечисляет всё, из чего значение
посчитано, и сравнивается при чтении: ключ прежний — отдаём хранимое, ключ
изменился — пересчитываем. Проверка годности лежит у читателя, и тот, кто
меняет источник, о хранимом значении может не знать.

```kotlin
// во ViewModel: результат как StateFlow
val filtered = combine(items, query) { list, q -> list.filter { it.matches(q) } }
    .distinctUntilChanged()
    .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), emptyList())

// в composable, входы под рукой
val sorted = remember(items, sortKey) { items.sortedBy(sortKey) }

// в composable, вход читается на каждый кадр
val showButton by remember { derivedStateOf { listState.firstVisibleItemIndex > 0 } }
```

Два правила для ключа:

- В ключе все входы. `remember(query) { items.filter(...) }` залипнет на
  старом списке, когда обновится `items`: читатель проверяет годность по
  неполному перечню.
- Ключ сравнивается по значению. `ByteArray` сравнивается по ссылке, поэтому
  `remember(bytes) { decode(bytes) }` при повторной загрузке тех же байтов
  декодирует заново. Ключом берут `url` или хэш.

Это и есть граница между кэшем и вторым источником истины: кэш — хранимое
значение плюс ключ, по которому читатель сам решает, годно ли оно. Второй
источник истины — хранимое без ключа, где годность держится на дисциплине
писателей.

## Почему хранимое поле расходится

```kotlin
data class CartState(val items: List<CartItem>, val totalPrice: Int)

fun addItem(s: CartState, i: CartItem) =
    s.copy(items = s.items + i, totalPrice = s.totalPrice + i.price * i.qty)

fun applyServerPrices(s: CartState, prices: Map<String, Int>) =
    s.copy(items = s.items.map { it.copy(price = prices[it.id] ?: it.price) })
```

Правило «`totalPrice` равен сумме `items`» принадлежит состоянию, а
поддерживают его писатели. Каждая функция, меняющая `items`, обязана
пересчитать сумму. `applyServerPrices` появилась позже и про сумму не знает.
Цепочка: добавили молоко по 100, сервер поднял цену до 120, добавили хлеб по 50.
В `items` 170, в поле 150. Каждый шаг по отдельности корректен, расходится
только последовательность — отсюда баги вида «если сначала А, потом Б».

Починка `applyServerPrices` закрывает один баг, а не класс: список писателей
открыт, завтра появится следующий. Единый редьюсер сужает круг, но не убирает
риск: четвёртая ветка `when` без пересчёта, и `copy()` с публичным
конструктором, которые доступны мимо редьюсера. Стенд показывает расхождение
для разрозненных писателей на втором шаге, для единого редьюсера на четвёртом
и пятом, для геттера — ни на одном. Убирает риск только отсутствие второго
слота: у геттера нет собственного состояния, которое можно не обновить.

## Чем платят за кэш

Хранимому значению нужно правило сброса: после каких событий оно негодно.
Поле без ключа требует помнить это правило в каждом писателе. Кэш с ключом
правило автоматизирует, но три платы остаются и у него:

- Сравнение ключа на каждое чтение. `items to query` сравнить дёшево, два
  массива по мегабайту — нет.
- Первое чтение после смены источника платит полную цену вычисления, и оно
  обычно происходит на UI-потоке.
- Источник обновился теми же данными: ключ формально новый, пересчёт дал тот
  же результат, экран перерисован зря. Лечится `distinctUntilChanged` после
  вычисления, то есть ещё одним сравнением.

## Как найти в чужом коде

1. В state найти поле, которое можно посчитать из соседних. Посчитать, сколько
   функций его пишут. Больше одной, или есть `copy()` снаружи — разойдётся.
2. В `remember` и `combine` сверить ключ с переменными внутри лямбды.
   Переменная внутри есть, в ключе нет — залипнет.
3. Баг «если сначала одно, потом другое, число неверное» — искать хранимое
   производное поле первым делом.

## Итог

Поле, которое получается из соседних полей прямо сейчас и всегда одинаково, —
производное. По умолчанию его вычисляют геттером: второго слота нет, расходиться
нечему. Если вычисление дорого и читается много чаще, чем меняется источник,
его хранят как кэш с ключом, где ключ перечисляет все входы и сравнивается по
значению при чтении. Поле без ключа — второй источник истины: правило
«пересчитай» держится на каждом писателе, список писателей открыт, единый
редьюсер и `copy()` мимо него риск не убирают. Хранят обычным полем только то,
что из текущего state не выводится: снимок на момент, случайность, ответ
другого процесса.
