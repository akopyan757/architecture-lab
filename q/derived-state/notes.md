## Карта разбора
1. Граница «кэш vs второй источник истины» (шатко)
2. Механизм рассинхрона хранимого производного поля (шатко → возможно с нуля)
3. Критерий «вычислять»: что именно сравнивают (с нуля)
4. Случаи обязательного хранения: снимок, недетерминизм, асинхронный источник (с нуля)
5. Цена хранения: инвалидация как правило сброса, где окупается (с нуля)
6. Доказательство: стенд `q/derived-state/` — две версии state рядом, сценарий расхождения, ADR

## Зафиксировано
- Блок 1. Кэш = хранимое значение + ключ, по которому ЧИТАТЕЛЬ сам решает, годно ли оно. Второй источник истины = хранимое без ключа, годность держится на дисциплине ПИСАТЕЛЕЙ. Room без updatedAt/etag — не кэш, а источник истины по выбору (раздел 4).
- Блок 2. Механизм рассинхрона: инвариант `totalPrice == sum(items)` принадлежит состоянию, а поддерживают его писатели; список писателей открыт. Починка одной функции закрывает баг, не класс. Единый редьюсер сужает круг (но ветки + публичный copy/конструктор возвращают риск). Убирает только отсутствие второго слота: `val totalPrice get() = ...` — неверное состояние невыразимо.
- Блок 3. Критерий, по порядку: (1) чистота — результат зависит только от источника; (2) стоимость × частота чтений против частоты изменения источника; (3) если «хранить» — только как кэш с ключом (remember(key), derivedStateOf, combine+stateIn), не как поле state. Ключ должен сравниваться по значению (ByteArray — по ссылке, ловушка).

## Где ошибся
- блок 1: на вопрос о механизме ответил ценой (сколько раз считаем) — симптом, не механизм; момент проверки (запись vs чтение) обошёл дважды, пришлось дать прямо.
- блок 2: на «что вернёт риск» назвал только «один писатель» — не увидел открытый список веток и публичный copy; после подсказки назвал.

- Блок 4. Хранить обязательно, когда значение не функция от ТЕКУЩЕГО источника: снимок на момент (priceAtCheckout), недетерминизм (orderNumber), другой процесс со своим временем (deliveryEstimate, isOnline). Это не нарушение SSOT — они сами источник истины для своего факта. isOnline хранится один раз, на границе с системой, внутри state — вход combine, не поле с мутацией.
- Блок 5. Плата за хранение — правило сброса (инвалидация). Кэш с ключом автоматизирует его. Остаток цены: сравнение ключа, полная цена на первом чтении после смены источника (UI-поток), лишняя эмиссия при обновлении теми же данными (distinctUntilChanged). Неполный ключ = дисциплина писателей, спрятанная в remember.
- Блок 6. Стенд derived.kt: A расходится на шаге 2 (новый писатель), B на шаге 4 (ветка без recount) и 5 (copy мимо reduce), C не расходится. ADR в adr.md.

## На повторение
1. В `reduce` все ветки зовут `recount()`, конструктор и `copy` сделаны private через фабрику `CartState.of(items)`. Остался ли хоть один путь собрать неверный totalPrice? Чем тогда B отличается от C по гарантии и чем платит?
2. Позиция, стоявшая «шатко» и поплывшая: кэш vs второй источник истины. Repository держит `MutableStateFlow<List<User>>`, заполненный из сети, Room нет. Это кэш или источник истины? Назови, где ключ и кто проверяет годность, и что изменится, если добавить `fetchedAt`.
3. `combine(items, query) { f, q -> f.filter { it.matches(q) } }.stateIn(scope, Eagerly, emptyList())`. Какое из «трёх плат» блока 5 здесь уже оплачено заранее, и в какой момент экран заплатит всё равно?
4. `unreadCount` в шапке чата: сервер присылает своё число, локально есть список сообщений с флагом `read`. Два кандидата в источник. По критерию блока 4 какой из них хранить, какой выводить, и что делать, когда они расходятся?
5. Перенос на рабочий код: открыть любой экран со списком и фильтром в текущем проекте. Найти поле state, которое выводится из других, и проверить по стенду: сколько у него писателей, есть ли путь `copy()` мимо них, есть ли ключ. Решить по критерию блока 3, оставить, вычислять или превратить в кэш.
