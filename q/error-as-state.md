# ошибка как часть состояния, а не исключение

Issue: [#16](https://github.com/akopyan757/architecture-lab/issues/16) · раздел: [1. Состояние и поток данных](../architecture-map.md)

**Доказано:** нечем — код в разборе модельный, не прогонялся. Две модели
одного экрана стоят рядом, трассировка на четыре шага выведена чтением по
шагам, а не снята с устройства.

## Механизм, из которого всё следует

`StateFlow` хранит одно последнее значение и отдаёт его каждому новому
подписчику. Всё, что лежит в состоянии, читается повторно: после поворота,
при новой подписке, через час. Из этого одного свойства вытекает и выигрыш, и
цена.

**Выигрыш.** Исключение, пойманное слоем выше и показанное один раз, не
оставляет следа. Если подписчика в момент сбоя не было — экран пересоздавался
после поворота, — показывать было некому, и новый UI выглядит так, будто всё в
порядке. Ошибка-значение в состоянии переживает отсутствие подписчика: новый
collector получает последнее состояние вместе с ошибкой.

**Цена.** Ошибка залипает. Обновление состояния по полям переносит всё, что не
названо:

```kotlin
fun refresh() = viewModelScope.launch {
    val result = runCatching { repo.load() }
    _state.update { s ->
        result.fold(
            onSuccess = { s.copy(items = it, error = null) },  // error = null — явный сброс
            onFailure = { s.copy(error = LoadError.Network) },
        )
    }
}
```

Без `error = null` успешная загрузка оставит старую ошибку на экране рядом со
свежими данными. Сбросить её обязан тот, кто владеет состоянием, — ни
`StateFlow`, ни UI этого за него не сделают.

## Какая ошибка попадает в состояние

Вопрос к ошибке один: **можно ли показать её второй раз и не соврать?**

- «Не удалось загрузить» — **положение дел**: данные на экране устарели, и это
  верно, пока их не перезагрузят. Повторное чтение говорит правду → **state**.
- «Не удалось отправить» — **событие**: попытка случилась и закончилась, экран
  по-прежнему показывает актуальные данные. Повторное чтение превращает старый
  факт в мнимый новый → **effect**, отдельным каналом ([#11](state-event-effect.md)).

Критерий не про вид экрана. «Не удалось отправить» тоже появляется при
показанном списке и от этого не становится состоянием.

## Форма: sealed-only против data + error

```kotlin
// sealed-only: у Error нет поля items — значит в этом состоянии списка не существует
sealed interface ScreenState {
    data object Loading : ScreenState
    data class Error(val cause: LoadError) : ScreenState
    data class Content(val items: List<Item>) : ScreenState
}

// data + error: список и ошибка живут рядом
data class ScreenState(
    val items: List<Item> = emptyList(),
    val isLoading: Boolean = false,
    val error: LoadError? = null,
)
```

Один и тот же сценарий: на экране 20 элементов, `refresh` упал.

| Шаг | `sealed`-only | `data + error` |
|---|---|---|
| Исходное | `Content(20)` | `State(items=20, error=null)` |
| `refresh` упал | `Error(Network)`, 20 элементов потеряны | `State(items=20, error=Network)`, баннер над списком |
| Поворот | новый подписчик видит `Error` — экран пустой | видит те же 20 и баннер |
| Повторный `refresh` успешен | `Content(20)` после полной перезагрузки | `error=null`, баннер гаснет, список не мигал |

Потеря списка в левой колонке — следствие типа, а не недосмотр в UI: у `Error`
просто нет поля, где список мог бы лежать.

Правая модель позволяет различить первую загрузку и refresh по данным:
`items.isEmpty() && error != null` → полноэкранная ошибка с «Повторить»,
`items.isNotEmpty() && error != null` → баннер над списком.

Граница этого условия: пустой список может прийти и с сервера. Чтобы отличить
«ещё не загружали» от «загрузили, там пусто», нужен `items: List<Item>?`, где
`null` значит «данных ещё не было». Цена — проверки на `null` во всех местах,
где список читают.

## Кто гасит ошибку

Скрытие в UI не работает по тому же механизму, из которого всё началось:

```kotlin
var dismissed by remember { mutableStateOf(false) }   // не гасит ошибку
```

`dismissed` теряется при пересоздании, а `error` остаётся в `StateFlow` —
новый подписчик получает её снова, и баннер возвращается. Гасит владелец
состояния: `dismissError() = _state.update { it.copy(error = null) }`.

Выходов из ошибки ровно два: следующая загрузка (`refresh` / `retry`) и явный
`dismissError()`. Если не вызван ни один, ошибка залипает навсегда.

Опасный случай — `dismissError()` на полноэкранной ошибке, когда `items`
пуст. Получается пустой экран без ошибки и без «Повторить»: состояние
утверждает «данных нет», хотя на самом деле загрузка упала, и единственное
свидетельство сбоя стёрто. У полноэкранной ошибки выход должен быть один —
`retry`.

## Когда это не нужно

- **Нечего сохранять.** Экран деталей одной записи без записи бессмыслен:
  показывать при упавшей загрузке нечего, и `sealed` с полноэкранной ошибкой
  достаточен. `data + error` здесь только добавляет поле, которое всегда
  пусто.
- **Старые данные показывать нельзя.** Доступ отозван, на экране приватный
  список — нужна модель, которая данные убирает, а не оставляет рядом с
  ошибкой.
- **Старые данные допустимы — решает продукт.** Показывать, убирать или
  показывать с отметкой времени:

```kotlin
data class BalanceState(
    val balance: Money? = null,
    val updatedAt: Instant? = null,
    val error: LoadError? = null,
)
```

Допустимая устарелость значения — продуктовое решение, а не кодовое. Баланс,
по которому принимают решение о платеже, показывать устаревшим нельзя;
справку, которую читают, можно.

## Итог

Ошибка идёт в состояние, если она описывает положение дел, которое остаётся
верным при повторном чтении, и в эффект, если описывает случившееся событие.
В состоянии она переживает отсутствие подписчика — за это её туда и кладут, —
и по той же причине залипает, пока её явно не сбросят. Форма решает, что
останется на экране при упавшем refresh: у `sealed`-только-`Error` поля для
данных нет, поэтому данные исчезают; у `data + error` список остаётся, а
ошибка стоит рядом. Гасит её владелец состояния, и ровно двумя способами:
следующей загрузкой или явным `dismissError()` — причём второй способ нельзя
давать полноэкранной ошибке, иначе экран начинает врать про пустоту.
