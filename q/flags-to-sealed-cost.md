# стоимость миграции флаговой модели в sealed на живом проекте

Issue: [#83](https://github.com/akopyan757/architecture-lab/issues/83) · раздел: [7. Эволюция и деградация](../architecture-map.md)

**Доказано:** код в [`q/flags-to-sealed-cost/`](flags-to-sealed-cost/) — один и тот
же экран до и после миграции, плюс мост между двумя моделями. Цифры сняты на
модельном коде, не на проде, и это оговорено там же.

## Экран, о котором речь

Список заказов. Грузится, может упасть с ошибкой, может оказаться пустым.

Состояние сейчас — три поля:

```kotlin
data class OrdersState(
    val isLoading: Boolean = false,
    val error: String? = null,
    val orders: List<Order> = emptyList(),
)
```

Хотим так:

```kotlin
sealed interface OrdersState {
    data object Loading : OrdersState
    data class Error(val message: String) : OrdersState
    data object Empty : OrdersState
    data class Content(val orders: List<Order>) : OrdersState
}
```

Зачем — не тема этого разбора, это разобрано в
[sealed-vs-flags.md](sealed-vs-flags.md). Здесь один вопрос: **сколько это
работы на живом проекте.**

## Сколько мест придётся тронуть

Пятнадцать. Полный список:

| Где | Сколько |
|---|---|
| Само объявление `OrdersState` | 1 |
| Начальное значение во ViewModel | 1 |
| Места, где состояние менялось через `copy()` | 3 |
| Проверки полей в UI (`if (state.isLoading)` и т.п.) | 3 |
| Вызовы дочерних функций и их сигнатуры | 3 |
| Защита от повторной загрузки | 1 |
| Показ ошибки через `LaunchedEffect` | 1 |
| Аналитика и дебажный оверлей | 2 |

Пятнадцать звучит страшно, но одиннадцать из них правятся не думая: заменил
чтение поля на проверку варианта и пошёл дальше. Это работа на двадцать минут.

**Дорого стоят оставшиеся четыре.** Это не правки, а вопросы.

## Вопрос 1. Что показывать при открытии экрана

Раньше состояние по умолчанию собиралось само:

```kotlin
MutableStateFlow(OrdersState())   // не грузим, ошибки нет, список пуст
```

В новой модели такого варианта нет вообще. Надо выбрать явно — `Loading` или
`Empty`:

```kotlin
MutableStateFlow<OrdersState>(OrdersState.Loading)
```

Разница видна пользователю: спиннер при открытии или сразу «пусто».

## Вопрос 2. Пустой список — это что

Было одной строкой:

```kotlin
.onSuccess { items -> state.copy(isLoading = false, orders = items) }
```

Пустой ответ молча становился «списком из нуля элементов». Стало:

```kotlin
.onSuccess { items ->
    state.value = if (items.isEmpty()) OrdersState.Empty else OrdersState.Content(items)
}
```

Строка расщепилась надвое, потому что пустой экран и экран со списком — разные
состояния. Раньше это тоже было правдой, просто нигде не записано.

## Вопрос 3. Что делать со старым списком, если пришла ошибка

Самый дорогой. Было:

```kotlin
.onFailure { e -> state.copy(isLoading = false, error = e.message) }
```

Список `orders` при этом оставался лежать в состоянии. Показывать его или нет,
решал UI — и решал случайно, тем, в каком порядке шли `if`.

Стало: `Error` носит только сообщение, список **терять некуда**. Варианта два:

```kotlin
// либо теряем список
data class Error(val message: String) : OrdersState

// либо Error тащит его с собой
data class Error(val message: String, val lastKnown: List<Order>) : OrdersState
```

Второй вариант — это поле, общее для двух веток, со своей ценой (об этом в
конце [sealed-vs-flags.md](sealed-vs-flags.md)). Но выбрать придётся, и молча
уже не выйдет.

## Вопрос 4. Сколько раз показывать одну и ту же ошибку

Было — подписка на поле:

```kotlin
LaunchedEffect(state.error) { if (state.error != null) showSnackbar(state.error) }
```

Поля больше нет. Ближайшая замена — подписка на состояние целиком:

```kotlin
LaunchedEffect(state) { if (state is OrdersState.Error) showSnackbar(state.message) }
```

Поведение поменялось: две одинаковые ошибки подряд теперь дадут один показ
снекбара вместо двух. Правильное решение — вынести показ в отдельный поток
событий, но это уже второй рефакторинг внутри первого, и его лучше не начинать
в том же коммите.

## Итог по одному экрану

Одиннадцать механических правок и четыре решения. Причём все четыре решения
**были нужны и до миграции** — просто ответы на них давал конструктор по
умолчанию, молча и не всегда верно.

Пара мест стала даже проще. Например, при старте загрузки больше не нужно
помнить про `error = null`:

```kotlin
// было
state.copy(isLoading = true, error = null)   // забудешь — спиннер поверх старой ошибки
// стало
state.value = OrdersState.Loading
```

## Когда цена совсем другая: общий тип состояния

Всё выше верно, если `OrdersState` объявлен рядом с экраном и больше никто про
него не знает. Проверяется одной командой:

```bash
rg -l 'OrdersState' app/src
```

Если в выдаче только файлы «Заказов» — цена та, что выше, и можно мигрировать
одним коммитом.

Но часто в проекте есть один тип состояния на все экраны:

```kotlin
data class UiState<T>(
    val isLoading: Boolean = false,
    val error: String? = null,
    val data: T? = null,
)
```

«Заказы» берут `UiState<List<Order>>`, «Профиль» — `UiState<User>`, и так далее.
Файл один. Переделать его только под «Заказы» нельзя — переделаешь всем.

Тогда работа делится на две части:

- **разовая** — переписать общий тип и общий рендер. Стоит столько, сколько
  экранов им пользуются, умножить на пятнадцать. Три экрана — вечер работы.
  Сорок — одним коммитом уже нельзя.
- **на каждый экран** — те самые пятнадцать точек.

Важное следствие: **разовую часть оплачивает тот, кто мигрирует первым.** Если
измерить стоимость на первом экране и по ней судить обо всей миграции —
получится завышенная цифра, и от миграции откажутся зря. Мерить надо два экрана
подряд: первый и второй.

### Отдельно: «у нас уже sealed, мигрировать нечего»

Частый случай — в проекте есть `Resource<Loading | Error | Success>`. Ось
«загрузка / успех / ошибка» закрыта. А внутри:

```kotlin
data class OrdersContent(
    val orders: List<Order>,
    val isRefreshing: Boolean = false,
    val isSubmitting: Boolean = false,
)
```

Флаги вернулись этажом ниже, и `isRefreshing` вместе с `isSubmitting` — снова
комбинация, которой не должно быть. Вопрос на таком проекте другой: что из
внутренних флагов поднять до вариантов, а что оставить полем. Ответ тоже
разовый и тоже падает на первого.

## Если переделать всё сразу нельзя

Команда не останавливается, пока ты мигрируешь. Значит, обе модели какое-то
время живут рядом, и между ними нужен мост.

Мост строится **только в одну сторону** — из новой модели в старую:

```kotlin
fun OrdersState.toLegacy(): LegacyOrdersState = when (this) {
    OrdersState.Loading   -> LegacyOrdersState(isLoading = true)
    is OrdersState.Error  -> LegacyOrdersState(error = message)
    OrdersState.Empty     -> LegacyOrdersState(orders = emptyList())
    is OrdersState.Content-> LegacyOrdersState(orders = orders)
}
```

Четыре строки, ноль решений, один файл. Столько и стоит промежуточный период.

Обратно — не получится честно:

```kotlin
fun LegacyOrdersState.toNew(): OrdersState = when {
    isLoading && error != null -> TODO("грузим и одновременно ошибка — что это?")
    error != null && orders.isNotEmpty() -> TODO("ошибка поверх старых данных")
    ...
}
```

У плоской модели комбинаций больше, чем вариантов у sealed, и часть из них не
переводится никак. Причём второй `TODO` — это ровно вопрос 3, всплывший второй
раз.

Отсюда правило: **пишем только `toLegacy()`.** Понадобился обратный мост —
значит, старая модель всё ещё производит состояния, которых не должно быть, и
граница миграции выбрана не там.

И главное про мост: это единственная часть работы, которая **растёт сама по
себе**. Пятнадцать точек ты платишь один раз, а мост надо дописывать при каждом
новом варианте состояния — всё то время, пока он жив. Мост, который «уберём в
следующем спринте», превращается в постоянную статью расходов.

## Когда мигрировать не стоит

Не всякий экран это окупает. Три случая, когда флаги лучше оставить:

- **Состояние по сути одномерное.** Если это просто статус без разной полезной
  нагрузки на каждую ветку — sealed не даст ничего, кроме лишнего кода. Хватит
  `enum`.
- **Экран доживает.** Если его выпиливают через квартал, пятнадцать точек и
  четыре решения — плата за код, которого скоро не будет.
- **Тип общий, экранов много, мигрировать всё сразу нельзя, а мост держать
  некому.** Тогда честнее не начинать, чем начать и застрять с двумя моделями
  навсегда.

## Короткий ответ на вопрос

Перевод одного экрана — это **пятнадцать мест, из которых думать надо в
четырёх**, и по времени это меньше часа, если тип состояния принадлежит только
этому экрану.

Если тип общий — к этому добавляется разовая переделка общего типа, и её
оплачивает первый экран. Мерить стоимость миграции по первому экрану нельзя:
второй будет кратно дешевле.

А четыре решения, которые вылезут, — это не цена sealed. Это вопросы, на
которые в старой модели просто никто не отвечал.
