## Что в поле не выводится из значения

Правило валидации — чистая функция от значения. Значит из `value` выводится
`error`, из `value` и исходного снимка — «есть что сохранять». Не выводятся
ровно две вещи, и обе про взаимодействие, а не про данные:

- `touched` — поле получило и отдало фокус;
- `submitted` — была попытка отправки (живёт на форме, не на поле).

Их нет в значении ни в каком виде: их создаёт пользователь. Третья такая ось —
`edited`, факт хотя бы одного ввода; она нужна не всегда, и когда нужна — см.
раздел про `dirty`. Всё остальное производно, и минимальная модель поля
состоит из значения, снимка и одной оси:

```kotlin
data class Field(val value: String, val initial: String, val touched: Boolean = false)

val Field.error: String? get() = rule(value)        // выводится
val Field.isDirty: Boolean get() = value != initial  // выводится
fun Field.shownError(submitted: Boolean) = error?.takeIf { touched || submitted }
```

## Почему плоская модель не выражает гейт показа

Плоская модель — `text`, `error`, `isValid` тремя полями рядом. Сценарий из
прогона A: поле обязательное и пустое, пользователь зашёл в него и вышел,
ничего не введя.

```
шаг              A1 проверка сразу  A2 проверка в onChange  A3 оси
экран открыт     обязательное поле  —                       —
фокус в поле     обязательное поле  —                       —
blur             обязательное поле  —                       обязательное поле
тап «Сохранить»  обязательное поле  —                       обязательное поле, не отправлено
```

A1 кричит на пустом экране, до любого действия пользователя. A2 не показывает
ошибку ни на одном шаге: `onChange` не случился ни разу, и кнопка остаётся
серой без объяснения. Третьего варианта у плоской модели нет — `error` и
`isValid` считаются либо раньше, либо позже, а момент показа выразить нечем.

Дело не в оформлении. Прогон B берёт два случая с одним и тем же значением:
обязательное поле, которое не трогали, и обязательное поле, которое
пользователь очистил:

```
тронуто и очищено    text=«» error=обязательное поле isValid=false
не тронуто и пусто   text=«» error=обязательное поле isValid=false
```

Состояния равны посимвольно. Показ ошибки должен различаться — различать
нечем. На осях это разные состояния: `diff=true touched=true` против
`diff=false touched=false`.

## dirty: от факта правки или от диффа

Это две оси, отвечающие на разные вопросы. Прогон B1: исходное значение
«Иван», пользователь ввёл пробел и стёр его.

```
состояние:               value=«Иван» initial=«Иван» touched=true edited=true
dirty по факту правки    true    «Сохранить» активна → PATCH без изменений
dirty по диффу           false   «Сохранить» серая   → запроса нет
```

Отсюда разделение: **кнопкой «Сохранить» управляет дифф, показом ошибки —
`touched`/`submitted`**. Одно поле `isDirty` на обе роли даёт либо лишние
запросы, либо ошибку не в тот момент.

Цена диффа — снимок в состоянии: для формы из тридцати полей это копия всей
формы, а для полей-объектов (список адресов) ещё и равенство, которое надо
определить. Angular поэтому даёт `dirty` по факту правки и прямо оговаривает,
что он становится истиной, даже если значение вернулось к исходному: ось по
правке дешевле, но на вопрос «есть что сохранять» она не отвечает.

## Момент валидации — это ось в состоянии, а не ветка в UI

«Проверять на вводе / на blur / на submit» выглядит продуктовым решением, но
выражается только осями:

- на вводе — не нужно ничего (и получается A1: ошибка до первого касания);
- на blur — нужна `touched`;
- на submit — нужна `submitted`.

`submitted` не выводится из `touched`: второй заход прогона A — пользователь
не касался поля и сразу нажал «Сохранить». Без оси отправки ошибка не
показана, отправки нет, и экран так же глух, как A2; с осью — ошибка
появляется.

Выбирая момент валидации, выбираешь, какое поле обязано лежать в состоянии.
Поэтому это вопрос формы состояния, а не вопрос вьюшки.

## error: хранить или выводить

Хранить производное — значит держать кэш без инвалидации. Прогон C: три
правки адреса, на второй значение подставлено мимо пересчёта (восстановление
черновика — `copy(text = v)`).

```
C1 хранимый error
шаг 1: «ab@»       error=непохоже на адрес
шаг 2: «ab@b.c»    error=непохоже на адрес   <- про прежнее значение
шаг 3: «ab@b.co»   error=—

C2 выводимый error
шаг 2: «ab@b.c»    error=—                   расхождение невозможно
```

На шаге 2 адрес корректен, под полем ошибка про прежнее значение, кнопка
серая при валидной форме. Одного `copy` без пересчёта достаточно — и
состояние врёт.

Цена вывода на той же последовательности: хранить — 3 вызова правила (по
одному на обновление); выводить при трёх читателях на кадр (баннер,
активность кнопки, цвет рамки) — 9; выводить с мемоизацией по значению —
снова 3. Для правила из одного регэкспа обсуждать нечего.

Обсуждать стоит другой случай: асинхронная проверка («логин занят») не
выводится из значения вообще. Ей нужны свои поля — что проверяется и каков
ответ на **это** значение, — и это уже состояние запроса, а не ошибка поля.
Граница разбора: раздел 4.

## Флаг `isValid` выбрасывает доказательство

Прогон D, тот же сбой с подстановкой:

```
D1 submit доверяет флагу
после ручного ввода   text=«ab@b.c» error=— isValid=true
после подстановки     text=«ab@»    error=— isValid=true
submit при isValid    ушло на сервер: ab@

D2 submit требует разобранное значение
значение «ab@»        submit не вызван, форма показала: непохоже на адрес
значение «ab@b.c»     ушло на сервер: Email(ab@b.c)
```

`isValid` — утверждение о прошлом значении, и ничто в типе не связывает его с
текущим. Если `submit` принимает не `String`, а `Email` с приватным
конструктором, собрать запрос без разбора нечем: ветки «проверено, но
невалидно» просто не существует.

Это та же мысль, что в предыдущем разделе, доведённая до границы: из
состояния убирается `error`, из подписи `submit` — `isValid`. В обоих случаях
убирается кэш проверки, а не проверка.

## Когда это нужно на практике

1. **Обязательное поле на форме создания.** Нужны обе оси: `touched` — чтобы
   «обязательное поле» не кричало на только что открытом экране, `submitted` —
   чтобы отправка не отказывала молча на поле, которого человек не коснулся.
   Прогон A показывает оба отказа плоской модели: A1 ругается до любого
   действия, A2 не ругается вообще.
2. **Форма редактирования с кнопкой «Сохранить».** Нужен `dirty` именно от
   диффа со снимком. От факта правки (`edited`) кнопка остаётся активной после
   «ввёл пробел и стёр» — прогон B1, и это уходящий на сервер PATCH без
   изменений. Тот же дифф даёт предупреждение о несохранённых изменениях при
   уходе с экрана.
3. **Ошибку показывают в двух местах** — под полем и сводкой сверху, или ещё
   цветом рамки. Выводимый `error` даёт один факт на всех читателей; хранимый
   обязан обновляться в каждой ветке, которая трогает значение, и прогон C
   показывает цену пропуска одной такой ветки.
4. **Черновик восстанавливается не вводом** — из сохранённого состояния, с
   бэкенда, автозаполнением, deeplink'ом. Это и есть ветка, где хранимый
   `error` разъезжается с значением, а `isValid` врёт: прогон D1 отправляет
   `ab@` с флагом «проверено».
5. **Значение уходит дальше в домен или в сеть.** Нужен тип с приватным
   конструктором: он убирает из кода ветку «проверено, но невалидно», а не
   добавляет ещё одну проверку.

**Когда не нужно ничего.** Поле поиска по списку: нет отправки, нет исходного
снимка, нет понятия «валидно» — только значение и выводимый из него результат
фильтрации. `touched`, `edited`, `submitted` заводят там по шаблону, и они
просто висят в состоянии, расширяя пространство состояний без причины.

Признак, по которому ось заводят, один: **её нельзя вывести из значения.**
`touched` и `submitted` создаёт пользователь, поэтому они в состоянии. `error`
и дифф — функции от значения, поэтому их там быть не должно.

## Границы

- Агрегация формы из полей — OR по `touched`, AND по валидности, и что делать
  с выключенными полями — отдельный вопрос, здесь не разбирается.
- Кто владеет состоянием поля — сам компонент ввода или держатель формы —
  [#12](https://github.com/akopyan757/architecture-lab/issues/12).
- Серверная валидация и формат ошибок API — раздел 4. Клиентская проверка
  никогда не единственная: она про момент показа, а не про истину.

## Итог

В состоянии поля лежит значение, исходный снимок и факты о взаимодействии —
`touched` у поля, `submitted` у формы. Всё остальное выводится: ошибка из
значения, «есть что сохранять» из диффа со снимком. Плоская модель с
`error` и `isValid` полями ломается не на оформлении, а на том, что «не
тронуто и пусто» и «тронуто и очищено» становятся в ней одним состоянием —
гейт показа выразить нечем. Момент валидации выбирается осями, а не ветками в
UI. Хранимое производное — кэш без инвалидации: одного обновления значения
мимо пересчёта достаточно, чтобы под корректным адресом стояла ошибка про
прежний, а `submit` отправил непроверенное значение с флагом «проверено».
