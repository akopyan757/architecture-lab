# MVI / MVVM / MVP: что реально различается

## Три оси, а не три ступеньки

Если открыть три реализации и стереть имена классов, различать их будут ровно
три признака.

**Направление связи.** В MVP презентер держит ссылку на экран и командует ей:

```kotlin
interface ItemsView {
    fun showLoading()
    fun showItems(items: List<Item>)
    fun showError(message: String)
}
```

В MVVM и MVI этой ссылки нет: экран подписан на то, что отдаёт ViewModel.

**Форма состояния.** В MVP актуального состояния нет ни одного поля — что
сейчас на экране, знают только виджеты. В MVVM состояние переехало в VM, но
обычно лежит набором независимых полей. В MVI — одним объектом.

**Форма ввода.** Вызов метода презентера, вызов метода VM или типизированное
намерение (`Intent.Retry`).

| | MVP | MVVM | MVI |
|---|---|---|---|
| связь | push: `view.showX()` | подписка | подписка |
| состояние | нет, в виджетах | набор полей | один объект |
| ввод | метод презентера | метод VM | типизированное намерение |

Главное здесь — что оси **независимы**. MVVM, у которого состояние собрано в
один `data class`, остаётся законным MVVM, хотя по второй оси совпал с MVI.
Поэтому спор «MVVM или MVI» так часто разваливается: спорящие сравнивают разные
оси и оба правы по своей.

## Две оси сняла платформа

Интерфейс `View` умер не от моды. Чтобы вызов `view.showLoading()` имел смысл,
нужны адресуемый долгоживущий объект и его память: виджет помнит, что ему
сказали, пока не скажут иначе. В декларативном UI нет ни того, ни другого —
функция экрана вызывается заново на каждой рекомпозиции и рисует всё из
переданного значения:

```kotlin
@Composable
fun ItemsScreen(state: ItemsState, onIntent: (Intent) -> Unit) {
    if (state.isLoading) Spinner() else ItemList(state.items)
}
```

Крикнуть «покажи загрузку» здесь некому, а если крик нигде не записан —
следующая же перерисовка о нём не узнает. Отсюда требование, которое перестало
быть выбором: **актуальное состояние обязано где-то лежать целиком**, чтобы его
можно было прочитать в любой момент и сколько угодно раз. Тот же вывод без
Compose даёт пересоздание экрана: push требует живого получателя, подписка
переживает его смерть, потому что значение лежит в VM, а не в проводе.

Третья ось схлопывается следом. Возьмём MVVM и сделаем то, чего MVVM не
запрещает, — один объект состояния и одну точку входа:

```kotlin
class ItemsViewModel(private val repo: ItemsRepo) : ViewModel() {
    private val _state = MutableStateFlow(ItemsState())
    val state: StateFlow<ItemsState> = _state

    fun onEvent(event: ItemsEvent) = when (event) { /* ... */ }
}
```

Это ровно то, что обычно показывают как MVI, — различаются только слова
`Event` и `Intent`. Значит, из трёх осей две выбором быть перестали: они заданы
платформой, а не буквой в названии.

## Остаётся тотальность

Настоящий остаток не виден в типе поля. Он в вопросе: **обязаны ли все
изменения проходить через одну функцию** — или `_state.update {}` можно позвать
из любого метода класса.

Разницу показывает сценарий из [`race.md`](mvi-mvvm-mvp/race.md). Пользователь
жмёт «Повторить» дважды, летят два запроса, второй возвращается успехом раньше,
чем первый — таймаутом:

| шаг | событие | результат в наивной MVVM |
|---|---|---|
| t0 | нажал → запрос A | `loading=true` |
| t1 | нажал → запрос B | `loading=true` |
| t2 | **B: успех** | `loading=false, items=[…]` |
| t3 | **A: таймаут** | `loading=false, items=[…], error="таймаут"` |

На t3 на экране одновременно список и ошибка — состояния, которого в продукте
нет. При этом `MutableStateFlow` атомарен и каждая запись по отдельности
корректна; версия из [`mvvm.kt`](mvi-mvvm-mvp/mvvm.kt) с одним `data class`
приходит к той же строке. Сломался не доступ к полю, а **инвариант между
полями**: «items и error не бывают заполнены одновременно». Он нигде не
записан — охранять его нечем.

Тотальный вариант записывает его в единственном месте:

```kotlin
fun reduce(state: ItemsState, msg: Msg): ItemsState = when (msg) {
    Msg.Started -> state.copy(isLoading = true, error = null, requestId = state.requestId + 1)
    is Msg.Loaded -> if (msg.requestId != state.requestId) state
                     else state.copy(isLoading = false, items = msg.items, error = null)
    is Msg.Failed -> if (msg.requestId != state.requestId) state
                     else state.copy(isLoading = false, error = msg.message, items = emptyList())
}
```

Куплены ровно три вещи:

1. **Переходы перечислимы** — все способы изменить состояние суть ветки одного
   `when`. Инвариант проверяется чтением одной функции, а не поиском
   `_state.update` по всему классу.
2. **Устаревший ответ отбрасывается** — переход получает текущее состояние
   аргументом и может сравнить с ним номер запроса.
3. **Переход тестируется без корутин** — `reduce(state, msg)` чистая: вход,
   выход, ни диспетчеров, ни моков.

Чего в списке нет: производительности, «реактивности» и «меньше багов вообще».

## Цена

- **Изменение — три места**: тип сообщения, ветка `reduce`, вызов. Одно поле —
  уже не одна строка.
- **`reduce` обязан быть чистым**, поэтому запуск запросов выселяется наружу.
  На экране появляется второй поток управления, а маршрут кнопки растягивается
  на `Intent → запуск → Msg → reduce` вместо одного метода.
- **Читаемость меняет знак**: «где меняется `isLoading`» стало тривиально, «что
  произойдёт по кнопке» — хуже.
- **Рост `when`**: на экране с двумя десятками сообщений редьюсер читают по
  диагонали, и перечислимость перестаёт работать ровно там, где была нужна.

## Когда это окупается

Считать надо не поля, а **независимых писателей** в одно состояние:
пользователь; каждый параллельный сетевой ответ; подписки, приходящие сами
(пуш, сокет, таймер); системные события. Экран с пятнадцатью полями формы,
которые меняет только пользователь, прекрасно живёт на обычных полях — ломаться
там нечему.

Порядок действий, первое совпадение — ответ:

1. Состояние живёт в VM и наблюдаемо — обязательно, это не выбор.
2. Между полями есть инвариант — вырази его типами: `sealed` вместо набора
   флагов. Часть невозможных комбинаций исчезает бесплатно.
3. Писателей больше одного и инвариант остался — тотальный `reduce` плюс
   признак актуальности ответа.
4. Иначе — поля и `update`, без церемонии.

Пункт 2 стоит раньше пункта 3 осознанно: типы убирают часть проблемы даром,
тотальность — за бойлерплейт. Начинать с редьюсера, пропустив второй пункт, —
самый частый способ получить большой `when`, который всё ещё допускает
`loading = true` вместе с `error`.

Решение принимается **на экран, а не на приложение**: число писателей у ленты с
пушами и у формы профиля разное, значит и ответ разный. Возражение «зато
единообразие» слабое, потому что шов проходит по границе ViewModel — наружу оба
варианта отдают наблюдаемое состояние и принимают одну функцию ввода, и экран
не знает, что у него внутри.

## Ответ в одну строку

Различаются не буквы, а готовность платить бойлерплейтом за перечислимость
переходов. Всё остальное на современном стеке либо задано платформой, либо
доступно в любой из трёх букв.
