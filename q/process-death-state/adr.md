# ADR: куда кладётся состояние экрана «Поиск квартир»

**Статус:** принято · **Проверка на устройстве:** не проводилась, решение
снято с рассуждения. Как перепроверить — в конце.

## Контекст

На экране поиска:

- строка поиска `"двушка у метро"`;
- фильтры: цена до 80k, 2 комнаты;
- список из 40 результатов, прокручен до 25-го;
- открыта карточка квартиры `id=742` с набранным «Сообщением владельцу»;
- висит snackbar «Добавлено в избранное»;
- пользователь залогинен.

Нужно решить, что должно пережить два разных сценария:

1. **Смерть процесса.** Приложение свёрнуто, система убила процесс,
   пользователь вернулся через recents.
2. **Явное закрытие.** Пользователь сам смахнул приложение из recents и
   открыл его заново.

## Варианты

Для каждого поля есть три корзины:

| Корзина | Переживает смерть процесса | Переживает явное закрытие | Механизм на Android |
|---|---|---|---|
| **(а) пересчитываемое** | восстанавливается из (б)/(в) | восстанавливается из (б)/(в) | ViewModel в памяти + повторная загрузка |
| **(б) UI-state** | ✅ | ❌ | saved state (`SavedStateHandle`, `rememberSaveable`) |
| **(в) persisted** | ✅ | ✅ | диск / сервер |

## Решение

| Поле | Корзина | Почему | Что будет в соседней корзине |
|---|---|---|---|
| Сессия | (в) | Пользователь ждёт, что останется залогинен и после явного закрытия | В (б): после смахивания из recents придётся логиниться заново |
| Текст сообщения владельцу | (в), черновик | Набранный текст больше неоткуда взять, потеря злит сильнее всего | В (б): текст теряется при явном закрытии. В (а): теряется даже при смерти процесса |
| Запрос и фильтры | (б) | Нужны, чтобы вернуть экран, но после явного закрытия ожидается чистый поиск | В (в): после явного закрытия всплывает старый поиск. В (а): восстановить список не из чего |
| Открытая карточка | (б), **только `id`** | По id квартира загружается заново | Вся квартира в (б): второй источник истины и риск `TransactionTooLargeException` |
| Позиция скролла | (б), **id якорного элемента**, а не индекс | После перезагрузки список может быть другим, индекс указывает не туда | Индекс в (б): попадаем на чужую квартиру. В (а): каждый раз наверх |
| Список из 40 результатов | (а) | Однозначно получается из запроса и фильтров | В (б): Bundle пухнет, данные из него устаревают |
| Snackbar | ничего, это эффект | Потеря эффекта при смерти процесса допустима, см. [#11](../state-event-effect.md) | В (б): snackbar показывается повторно после восстановления |

## Предпосылки (можно перепроверить)

1. **Буфер Binder около 1 МБ на процесс, общий для всех транзакций.** Google
   советует держать saved state в пределах десятков КБ. Если лимит вырастет на
   порядки, довод «только ключи» из-за размера ослабеет, но довод из-за SSOT
   останется.
2. **Список однозначно получается из запроса и фильтров.** Если выдача
   персонализирована или рандомизирована, «тот же список» не восстановить, и
   решение для списка надо пересматривать.
3. **Потеря набранного текста недопустима.** Это продуктовое решение, а не
   закон. Если продукт готов терять черновик, сообщение уходит в (б).
4. **Сервер — SSOT по квартирам.** Восстановленный `id` сверяется с ним, а не
   наоборот.

## Последствия

- Восстановление обязано выдерживать ключ, который никуда не ведёт.
  Квартиру `742` могли снять, пока процесс был мёртв, и у карточки появляется
  состояние «объявление снято» (пересечение с
  [#16](https://github.com/akopyan757/architecture-lab/issues/16)).
- Якорь скролла мог исчезнуть из новой выдачи. Нужен fallback: ближайший
  соседний элемент или начало списка.
- Черновику нужен свой жизненный цикл: когда он удаляется (после отправки) и
  к чему привязан (`id` квартиры).

## Как перепроверить на устройстве

1. Открыть экран в описанном состоянии и свернуть приложение.
2. Выполнить `adb shell am kill <package>` и вернуться через recents.
   Ожидание: восстановлены запрос, фильтры, карточка 742, скролл и черновик;
   snackbar не показан.
3. Смахнуть приложение из recents и открыть заново. Ожидание: сессия и
   черновик на месте, поиск чистый.
