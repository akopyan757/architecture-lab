## Короткий ответ

`MutableStateFlow.value` атомарен на каждом шаге по отдельности — но
`state.value = state.value.copy(...)` это три шага: чтение, вычисление, запись.
Атомарности нет **у окна между чтением и записью**, и всё, что случилось в этом
окне, запись затирает.

Сдвиг в том, что чинится это не «более свежим чтением», а тем, что решение и
запись становятся одной неделимой операцией. Отсюда три стратегии — CAS,
сериализация, отмена предыдущей — и четвёртая ось, ортогональная им:
идемпотентность, которая про повтор *намерения*, а не про порядок записей.

## Что ломается: потерянное обновление

Тысяча корутин на `Dispatchers.Default`, каждая делает один инкремент через
чтение-изменение-запись:

```kotlin
val snapshot = state.value                                  // чтение
state.value = snapshot.copy(count = snapshot.count + 1)     // запись
```

Три прогона подряд: **999, 977, 977** из 1000. Тело выполнилось ровно 1000 раз —
теряются не вызовы, а записи: две корутины прочитали одно и то же значение, обе
записали `snapshot + 1`, второй инкремент не случился.

Число недетерминировано и обычно маленькое — окно короткое. Это и есть ловушка:
на экране такое воспроизводится раз в неделю у одного пользователя.

Окно закрыто только если одновременно: все писатели живут на одном потоке **и**
между чтением и записью нет `suspend`. Однопоточный фоновый диспетчер этого не
даёт: фон + Main — уже два потока, и ответ сети, пришедший на фоне, конкурирует
с тапом на Main.

Затирание симметрично. Не «сеть побеждает пользователя»: кто записал вторым, тот
и стёр — ответ `refresh` стирает переключатель, а через миллисекунду наоборот.

## Второй режим: недостижимая комбинация

Второй режим менее заметный и более неприятный: **ничья запись не потеряна,
каждое поле по отдельности корректно, а пара нарушает инвариант.**

Инвариант экрана: `user != null` ⟺ `isLoggedIn == true`. Обновление профиля
прочитало состояние `(isLoggedIn = true, user = "старый профиль")`, ушло в сеть;
пока оно летело, пользователь вышел. Из прогона:

```
после logout:                 Session(isLoggedIn=false, user=null)
запись из снимка:             Session(isLoggedIn=true,  user=Иван)   <- logout стёрт
CAS без проверки:             Session(isLoggedIn=false, user=Иван)   <- logout цел, инвариант нарушен
CAS с проверкой внутри:       Session(isLoggedIn=false, user=null)   <- ответ отброшен, инвариант цел
```

Вторая строка — потерянное обновление из прошлого раздела: пишем все поля из
своего снимка, чужой `logout` исчезает.

Третья — суть этого раздела. Свежее чтение перед записью сделано, `logout` цел,
`copy(user = ...)` трогает только своё поле — и всё равно на экране
разлогиненный пользователь с именем. Потому что **устаревшим было не чтение, а
решение**: «положить профиль» приняли по снимку, в котором вход ещё был. Свежее
чтение устаревшее решение не лечит.

Отсюда правило: частичный `copy()` безопасен ровно тогда, когда между полями
нет инварианта. Есть инвариант — писать надо не поле, а переход, вместе с
условием, при котором он имеет смысл (четвёртая строка).

## Три стратегии

**CAS — `update {}`.** Оптимистичная: никого не блокирует, а перед записью
сверяет, что состояние всё ещё то, от которого считали. Не то — лямбда
пересчитывается от свежего значения. Результат сходится всегда: 1000 из 1000 в
каждом прогоне. Но лямбда выполняется **1038, 1045, 1053** раза — лишние вызовы
это проигранные гонки.

Из этого два следствия:

1. **Лямбда обязана быть чистой.** Ни сети, ни логов, ни аналитики: её вызовут
   несколько раз, и «несколько» заранее неизвестно.
2. **Защищено только то, что внутри лямбды.** `if (state.value.isLoggedIn) { ...
   state.update { ... } }` — проверка снаружи, между ней и записью то же окно.
   Внутри — `update { if (it.isLoggedIn) it.copy(user = u) else it }` — проверка
   и запись неделимы.

После проигранной гонки остаётся вопрос, который `update` сам не решает: нужна
ли ещё работа по новому снимку? Для профиля после `logout` — нет, ответ просто
выбрасывается. Для «пересчитать сумму по корзине», когда в корзину успели
добавить товар, — да, и это уже внешний повтор: `updateAndGet` и пересчёт, пока
вход не совпадёт с тем, от которого считали.

**Сериализация — `Mutex`.** Пока одна мутация держит лок, остальные ждут.
Устаревших снимков нет, повторов нет: 1000 из 1000 при ровно 1000 выполнений
тела. Цена в другом месте — лок берётся через `suspend`, то есть его можно
держать через сетевой вызов, и тогда каждая мутация ждёт самую долгую секцию.

Разница одной строкой: **CAS — никто не ждёт, но работа может повториться;
Mutex — работа делается один раз, но остальные ждут.**

И общая для лока оговорка: он защищает, только если в дисциплине **все**
писатели. Один `removeItem` под локом и один `addItem`, пишущий напрямую из
своего снимка, — и удаление снова теряется. Слепая запись ничего не проверяет,
ей нечем заметить, что лок кем-то занят.

**Отмена предыдущей — latest-wins.** Два запроса в полёте, старый ответ приходит
позже и пишется поверх свежего. Лечится тем, что новая операция отменяет
предыдущую (`job?.cancel()`), а не тем, как устроена запись.

Граница у этой стратегии узкая: она верна, только если новая операция делает
старую бессмысленной. Поиск — да: результат для «ко» никому не нужен, когда в
поле уже «кот». `addItem` — нет: отменённое добавление это потерянный товар, а
не устаревший результат.

## Когда это нужно на практике

Признак, по которому выбирают, — не «насколько важна операция», а какого рода
работа идёт между чтением и записью:

1. **Новая операция делает старую бессмысленной** — latest-wins. Поиск,
   автодополнение, перезагрузка ленты по pull-to-refresh: всё, где ценен
   результат последнего ввода, а не все результаты подряд.
2. **Короткое чистое изменение без `suspend`** — CAS. Счётчик, переключатель,
   отметка «прочитано», приход элемента из сокета. Лямбда должна пережить
   повтор — это дешевле, чем кажется, потому что она и так только `copy`.
3. **Долгая секция, которую нельзя выполнить дважды** — сериализация. Запись в
   базу, транзакционное изменение нескольких сущностей, миграция. Держать лок
   через сеть стоит осознанно, а не «раз он suspend, значит можно».
4. **Повтор намерения с эффектом вне состояния** — ключ идемпотентности
   (следующий раздел). Заказ, платёж, отправка сообщения.
5. **Долгое вычисление плюс частые конкурирующие записи** — ни то ни другое
   в чистом виде: CAS не сходится (каждый пересчёт успевают обогнать), Mutex
   тормозит всех. Тогда дорогое считают снаружи, а внутрь `update` кладут
   дешёвое чистое «наложить готовый результат на свежий снимок» — и там же
   проверяют, что вход не изменился.

**Когда не нужно ничего:** один писатель. Экран, где состояние меняет только
`ViewModel` в ответ на события UI, без фоновых подписок и без ответов сети,
приходящих сами по себе, гонок не даёт — и тащить туда `Mutex` значит платить
за проблему, которой нет.

## Повтор намерения: не гонка записей

Пользователь нажал «Оформить заказ», ответ не дошёл по таймауту, он нажал ещё
раз. Ни одна из трёх стратегий здесь не помогает, потому что проблема не в
порядке записей в состояние: `Mutex` аккуратно сериализует два запроса и даст
**два заказа**, latest-wins отменит первый и даст два или ноль.

Из прогона:

```
без ключа, 1 намерение + ретрай: заказов 2 [order-1, order-2]
с ключом,  1 намерение + ретрай: заказов 1 [order-1]
двойной тап, признак «в полёте»: запущено операций 1
```

Работают две разные вещи:

- **Признак «в полёте» в состоянии**, захватываемый атомарно:
  `getAndUpdate { if (it.inFlight) it else it.copy(inFlight = true) }` — вернул
  состояние, где `inFlight` уже был, значит операцию запустил кто-то другой.
  Это отсекает двойной тап, но не ретрай: ретрай — законный повтор, его гасить
  нельзя.
- **Ключ операции.** Создаётся клиентом в момент первого тапа, живёт **в
  состоянии экрана** и переиспользуется любым повтором — автоматическим и
  ручным. Сервер по ключу отдаёт уже созданный заказ вместо нового.

Ключ именно клиентский и именно заранее. `orderId` сервер выдаёт после
выполнения — в момент ретрая по таймауту его ещё не знает никто, ссылаться не
на что. И жить ключ должен не «в цикле ретраев», а в состоянии: иначе повтор
кнопкой создаст новый ключ и новый заказ.

Под этим лежит допущение о доставке: **таймаут не значит «не выполнено»**.
At-least-once — запрос мог дойти и выполниться, а потеряться уже ответ. Поэтому
повтор должен быть безопасен по построению, а не по надежде.

И отдельно: идемпотентность — не дебаунс. Дебаунс опирается на время («два тапа
за 300 мс — один»), идемпотентность — на ключ, и работает через час, через
перезапуск приложения и через смену сети.

## Границы

- **Ни одна стратегия не чинит устаревшее решение.** CAS гарантирует, что запись
  ляжет на то состояние, от которого считали, — но только если проверка живёт
  внутри лямбды. Снаружи всё то же окно.
- **CAS платит повторами**, и лямбда обязана их переживать. 1053 вызова на 1000
  инкрементов дешевы; 1053 похода в сеть — нет.
- **Mutex платит ожиданием** и держится только на дисциплине всех писателей:
  одна слепая запись мимо лока обнуляет защиту. Взятие того же мьютекса внутри
  секции, которую он охраняет, — дедлок: `Mutex` в kotlinx.coroutines не
  реентерабельный.
- **Latest-wins теряет данные по построению** — это не побочный эффект, а её
  контракт. Применять только там, где терять нечего.
- **Ключ идемпотентности требует второй стороны.** Клиентский ключ бесполезен,
  если сервер его не хранит и не сверяет.
- **Прогон здесь — модельный.** Это JVM без Android, без смены процесса и без
  реальной сети; он показывает механику окна и сходимость стратегий, а не
  частоту гонок в конкретном приложении.

## Итог

- `state.value = state.value.copy(...)` теряет обновления, потому что атомарен
  каждый шаг, а не окно между чтением и записью: 977 из 1000 в прогоне.
- Второй, более тихий режим — недостижимая комбинация полей: ничья запись не
  стёрта, но решение принималось по устаревшему снимку. Свежее чтение это не
  лечит, лечит перенос условия внутрь атомарного обновления.
- CAS и `Mutex` — обмен: повторы против ожидания. Latest-wins не про запись
  вообще, а про то, что старый ответ больше не нужен.
- Повтор намерения — отдельная ось. Признак «в полёте» гасит двойной тап, ключ
  операции переживает ретрай; и то и другое живёт в состоянии, а не в цикле
  запроса.
