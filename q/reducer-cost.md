## Что такое reducer

Функция, которая по текущему состоянию и случившемуся действию возвращает
новое состояние:

```kotlin
fun reduce(state: ItemsState, action: Action): ItemsState = when (action) {
    Action.Started,
    Action.Retried   -> state.copy(isLoading = true, error = null)
    is Action.Loaded -> state.copy(isLoading = false, items = action.items, error = null)
    is Action.Failed -> state.copy(isLoading = false, error = action.message)
}
```

Это вся конструкция. Кроме сигнатуры `(State, Action) -> State` от неё требуют
три вещи:

- **результат зависит только от аргументов** — внутри нет ни `now()`, ни
  `Random`, ни чтения чего-то глобального;
- **вход не меняется** — возвращается новый объект, старый остаётся целым;
- **наружу ничего не делается** — ни запроса, ни лога, ни навигации.

Главное следствие видно сразу: **`reduce` не умеет загружать**. `Action.Started`
не идёт в сеть, он только переводит экран в состояние «грузим». Запрос делает
кто-то другой и приносит обратно `Loaded` или `Failed`. Это не деталь
реализации — из этого вырастет вся цена.

Требования выглядят формальностью, пока не посмотреть, что ломает каждое
нарушение:

| нарушение | что перестаёт работать |
|---|---|
| `suspend fun reduce` или поход в репозиторий внутри | переход больше не мгновенный и не однозначный: результат зависит от того, что ответила сеть |
| `now()` или `randomUUID()` внутри | один и тот же список действий даёт разные состояния — сравнить в тесте нечего |
| `Log.e(...)` или `analytics.log(...)` внутри | прогнать 200 действий из баг-репорта в тесте теперь значит 200 записей в лог, а если это аналитика — 200 событий в прод-метрики |
| `state.items.add(x)` вместо `copy` | прежнее состояние испорчено: «до» и «после» — один и тот же объект, сравнивать нечего |

Отдельно стоит случай, который формально проходит, а по сути нет:

```kotlin
is Action.Failed -> state.copy(error = action.message.uppercase())
```

`uppercase()` чист, требования не нарушены — но в состояние кладётся уже
подготовленная для показа строка. Это логика отображения, заехавшая в переход.
Reducer от такого не защищает, это отдельная дисциплина.

## Что даёт

Всё видно только в сравнении, поэтому рядом — тот же экран без reducer'а
([`direct.kt`](reducer-cost/direct.kt)):

```kotlin
fun onOpen() {
    _state.update { it.copy(isLoading = true, error = null) }   // [1]
    load()
}

fun onRetry() {
    _state.update { it.copy(isLoading = true) }                 // [2] error = null забыт
    load()
}
```

Классический баг: нажал «Повторить» после неудачи — спиннер крутится поверх
старого текста ошибки. Пошаговая трассировка — в [`replay.md`](reducer-cost/replay.md).

**Одно место записи.** В `direct.kt` состояние присваивается в четырёх местах,
и с ростом экрана их станет восемь. Правило «пока грузим, старой ошибки на
экране нет» нигде не записано: оно существует как совпадение строк в разных
обработчиках. Чтобы поверить, что правило держится, надо прочитать все места и
держать их в голове разом. В `reduced.kt` это одна ветка `when`, которую видно
целиком.

**История становится данными.** Состояние экрана — результат сворачивания
списка действий:

```kotlin
val finalState = actions.fold(ItemsState(), ::reduce)
```

Баг-репорт «открыл, упало, нажал повторить, загрузилось» перестаёт быть прозой
и превращается в `listOf(Started, Failed("нет сети"), Retried, Loaded(items))`.
Прогнал — увидел состояние, в котором оказался пользователь. В `direct.kt`
повторить это можно только по-настоящему: с подменённой сетью, которая сначала
падает, потом отвечает.

**Тест без машинерии.**

```kotlin
@Test fun `retry clears previous error`() {
    assertEquals(
        ItemsState(isLoading = true, error = null),
        reduce(ItemsState(error = "нет сети"), Action.Retried),
    )
}
```

Ни корутин, ни диспетчера, ни `runTest`, ни мока репозитория. Дело не в том,
что так приятнее писать: цена одного теста падает настолько, что покрыть все
переходы становится реалистично — а значит, их и правда покрывают.

**Чего reducer не даёт.** Он не сужает набор возможных состояний. `ItemsState`
с тремя независимыми полями допускает `isLoading = true` вместе с
`error = "…"` ровно так же, как раньше. Невозможные комбинации убирает форма
`State` — про это [#10](https://github.com/akopyan757/architecture-lab/issues/10)
([`sealed-vs-flags.md`](sealed-vs-flags.md)), а не наличие `reduce`. Reducer
делает перечислимыми **переходы**, а не состояния. Путать эти две вещи — самый
частый способ прийти к большому `when`, который всё ещё допускает
противоречивый экран.

## Чем платим

**Вторая половина перехода.** Загрузка никуда не делась — она переехала:

```kotlin
fun dispatch(action: Action) {
    _state.update { reduce(it, action) }

    when (action) {                    // второй when по тем же Action
        Action.Started,
        Action.Retried   -> load()
        is Action.Loaded,
        is Action.Failed -> Unit
    }
}
```

Знание о том, что делает `Retried`, теперь живёт в двух местах: `reduce` знает
про флаг загрузки, `dispatch` — про запрос. Это не недоделка, а прямое
следствие чистоты: раз `reduce` не имеет права ходить наружу, обязан
существовать кто-то, кто ходит. Как эту вторую половину оформить — `suspend`
рядом, отдельный обработчик эффектов или middleware — отдельный вопрос,
[#86](https://github.com/akopyan757/architecture-lab/issues/86).

**Рост `Action`.** На карточке товара действий четыре. На форме регистрации с
восемью полями — восемь типов только на ввод, плюс валидация, плюс отправка,
плюс ответ сервера. Каждое «пользователь что-то сделал» обязано стать
объявленным типом, даже если переход — одна строка `copy`.

**Дольше читать.** Вопрос «что будет по нажатию кнопки» в `direct.kt` решается
одним прыжком в метод. В `reduced.kt` — тремя: какой `Action` летит, какая
ветка `reduce` сработает, есть ли для него эффект. Для человека, который видит
код впервые, это дороже.

**Обвязка.** Диспетчер, последовательная обработка событий, скоуп — повторяются
в каждой ViewModel. Ровно на эту боль отвечает
[StateReducerFlow](https://github.com/linean/StateReducerFlow): машинерию
выносят в общий примитив, чтобы в VM осталась только `reduce`. Цена решаемая,
но это ещё одна сущность в проекте.

## Одна несимметрия

Напрашивается вывод, что мы просто поменяли одну ошибку на другую. В `direct.kt`
можно забыть `error = null` в одном из четырёх `copy`. В `reduced.kt` можно
забыть ветку во втором `when` — тогда состояние обновится, запрос не уйдёт, и
спиннер будет крутиться вечно. Читать в обоих случаях примерно столько же,
забыть можно и там и там.

По объёму чтения это действительно так. Разница в другом: **одну ошибку можно
сделать невозможной, другую нельзя.**

```kotlin
when (action) {
    Action.Started,
    Action.Retried   -> load()
    is Action.Loaded,
    is Action.Failed -> Unit   // явно, не через else
}
```

Без `else` добавление нового `Action` не соберётся, пока автор не скажет про
него в обоих местах. Ошибка «забыл ветку» перестаёт существовать как класс —
её ловит компилятор.

Для четырёх `copy` такого рычага нет в принципе. Не существует способа
заставить компилятор проверить, что во всех местах записи выставлено
`error = null`: это утверждение про содержимое `copy`, компилятору оно
недоступно. Остаётся только внимательность.

Две честные оговорки к этому.

Первая: всё сказанное верно, **только если убрать `else`**. С `else -> Unit`
это ровно размен шила на мыло, потому что проверка полноты выключена.

Вторая: тест на `reduce` вечный спиннер не поймает. `reduce` в этом баге
правильный, сломан обработчик эффектов, а он тестируется уже со всей
машинерией. Дешёвые тесты покрывают половину экрана; вторую — по обычным
расценкам.

Что действительно меняется на практике — куда смотреть при отладке. Данные на
экране неправильные → причина в `reduce`, читать одну функцию. Данные
правильные, но ничего не произошло → причина в обработчике эффектов, `reduce`
можно не открывать. В `direct.kt` эти два вопроса неразделимы: данные и эффект
лежат в одном методе.

## Брать целиком или кусок

Вопрос не «сложный ли экран», а три конкретных признака. Первый — сколько у
состояния независимых писателей: если данные меняет только пользователь, всё
происходит по очереди и путаться особо негде; если меняют сеть, таймер, пуш и
ответ с другого экрана — ошибки живут в стыках, и там reducer окупается.
Подробный порядок принятия решения разобран в
[#14](https://github.com/akopyan757/architecture-lab/issues/14)
([`mvi-mvvm-mvp.md`](mvi-mvvm-mvp.md)) и здесь не повторяется. Второй — связаны
ли поля между собой: шесть независимых переключателей ломать нечем,
`isLoading`/`error`/`items` — есть чем. Третий — бывают ли баги, которые
воспроизводятся только определённой последовательностью действий.

Интереснее то, что признаки могут расходиться. Карточка товара: писатель один,
пользователь, — по первому признаку reducer не нужен. Но поля связаны, и баг
«упало → повторил → загрузилось, а ошибка висит» именно там и живёт.

Правильный ответ для такого экрана — **взять из reducer'а одну вещь, а не
паттерн целиком**:

```kotlin
private fun ItemsState.loading() = copy(isLoading = true, error = null)

fun onOpen()  { _state.update { it.loading() }; load() }
fun onRetry() { _state.update { it.loading() }; load() }
```

Это не reducer: нет иерархии `Action`, нет единого входа, нет обработчика
эффектов. Но правило «поднять загрузку и снять ошибку» стало одной строкой, и
разойтись двум обработчикам больше негде. Заплатили за это одной приватной
функцией вместо трёх новых сущностей.

Полную цену — `Action`, `dispatch`, отдельная вторая половина — имеет смысл
платить там, где у состояния несколько независимых писателей: лента с пушами,
чат, экран с фоновой синхронизацией. Решение принимается на экран, а не на
приложение.

## Ответ в одну строку

Reducer не убирает ошибки, а переносит их туда, где часть из них ловит
компилятор, — и берёт за это вторую половину перехода, которую надо где-то
держать. На экране с одним писателем полезное из него сводится к одной
приватной функции, и платить больше незачем.
