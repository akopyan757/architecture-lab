# когда sealed-иерархия сама становится долгом

Issue: [#84](https://github.com/akopyan757/architecture-lab/issues/84) · раздел: [7. Эволюция и деградация](../architecture-map.md)

**Доказано:** код в [`q/sealed-as-debt/`](sealed-as-debt/) — один и тот же экран
в двух формах рядом: [`grown.kt`](sealed-as-debt/grown.kt) (11 вариантов, 8
объявлений `orders`, переход `startRefresh` на 11 случаев) и
[`hybrid.kt`](sealed-as-debt/hybrid.kt) (4 варианта, 1 объявление `orders`,
тот же переход в 3 строки) при одном и том же множестве состояний. Цифры сняты
на модельном коде, не на проде.

`sealed` берут, чтобы невозможное состояние нельзя было построить: экран не
может одновременно грузиться и показывать ошибку, поэтому пусть это будут
разные варианты типа, а не два независимых поля. Форма работает, пока у экрана
одна ось. Здесь — что с ней происходит, когда осей становится больше, и в
какой момент она сама превращается в тот долг, от которого уходили.

## Алгебра состояний

Всё, что дальше, — следствия из одного факта: тип есть множество значений, и у
этого множества есть размер.

`Boolean` — два значения. `Unit` — одно. `Order?` — на одно больше, чем
`Order`. Размер множества значений типа называют **кардинальностью**; для
разговора о состоянии экрана это единственная характеристика типа, которая
важна, потому что «сколько состояний может быть у экрана» — это ровно она.

Две конструкции языка собирают из типов новые, и обе делают это арифметически.

**Произведение — это «И».** `data class` требует все поля одновременно,
значений у него столько, сколько сочетаний значений полей:

```kotlin
data class A(val x: Boolean, val y: Boolean)   // |A| = 2 × 2 = 4
```

**Сумма — это «ИЛИ».** `sealed interface` требует ровно один вариант, значений
у него столько, сколько дают варианты вместе:

```kotlin
sealed interface B {            // |B| = 1 + 1 + 1 = 3
    data object P : B
    data object Q : B
    data object R : B
}
```

Отсюда два названия: произведение (`×`) и сумма (`+`). Их комбинации и
называют алгебраическими типами — состояние экрана всегда записано каким-то
алгебраическим выражением, вопрос только в том, каким именно.

### Чего мы от формы хотим

Домен — то, что реально бывает на экране, — тоже множество. Хорошая форма это
множество воспроизводит: **кардинальность типа равна числу осмысленных
состояний.** Отсюда два разных вида несоответствия, и их нельзя путать, потому
что лечатся они по-разному.

**(а) Тип разрешает больше, чем домен.** Три флага дают восемь сочетаний, из
которых «грузим и показываем ошибку» невозможно. Лишние значения существуют, и
однажды кто-то их построит. Лечится сужением — и сужение **необратимо**: часть
значений перестаёт быть выразимой, и про каждое надо решить, чем оно теперь
становится. Это работа с продуктом, а не с кодом.

**(б) Тип разрешает столько же, но записан другой алгеброй.** Кардинальность
совпадает, множества состояний изоморфны — между ними есть отображение
один-в-один, ничего не теряется. Лечится переписыванием выражения, и это
работа механическая: продуктовых вопросов не возникает, потому что ни одно
состояние не исчезает.

Случай (а) — общеизвестный, за ним и идут в `sealed`. Разросшаяся иерархия —
случай (б), и именно поэтому её так трудно заметить: она не даёт багов
«невозможного состояния», гарантии не нарушены, счётчик сходится. Плохо в ней
не множество, а **структура записи**.

### Дистрибутивность

Один закон алгебры отвечает за всё, что будет дальше:

```
A × (B + C)  ≅  A × B + A × C
```

Слева — произведение: «есть A, и при этом одно из B или C». Справа — сумма
двух произведений: «или A с B, или A с C». Кардинальность одна и та же,
множества изоморфны, а записи разные. Правую часть называют дисъюнктивной
нормальной формой — суммой произведений.

Раздувшаяся `sealed`-иерархия — это и есть правая часть, раскрытая руками. Три
независимые оси поверх контента дают `Content × 2 × 2 × 2`; разложив это по
дистрибутивности, получаешь восемь слагаемых, и каждому приходится дать имя.
Гибрид — та же формула слева, нераскрытая.

Отсюда вся практика вопроса сводится к двум операциям школьной алгебры:
**раскрытие скобок** — то, что делает иерархия, растущая вариантами; и
**вынесение общего множителя** — то, чем это лечится.

## 1. Откуда берётся комбинаторный рост

Экран заказов. Состояние — четыре варианта на одной оси «что сейчас на
экране»:

```kotlin
sealed interface OrdersState {
    data object Loading : OrdersState
    data class Error(val message: String) : OrdersState
    data object Empty : OrdersState
    data class Content(val orders: List<Order>) : OrdersState
}
```

Форма держится, пока ось одна. Дальше приходит продукт, по одному требованию
за квартал:

- **R1.** Pull-to-refresh: обновляем, но список уже показан.
- **R2.** Оффлайн: данные из кэша, нужна плашка «данные от такого-то».
- **R3.** Режим выделения: чекбоксы поверх списка.

Каждое добавляется так, как подсказывает форма — новым вариантом. Через три
квартала в [`grown.kt`](sealed-as-debt/grown.kt) **одиннадцать вариантов**: три
на исходной оси и восемь на контенте — `Content`, `ContentRefreshing`,
`ContentOffline`, `ContentOfflineRefreshing`, `ContentSelecting`,
`ContentSelectingRefreshing`, `ContentSelectingOffline`,
`ContentSelectingOfflineRefreshing`.

### Восемь — это не «накопилось», это 2³

| Осей поверх контента | Вариантов контента | Всего в иерархии |
|---|---|---|
| 0 | 1 | 4 |
| 1 (`refreshing`) | 2 | 5 |
| 2 (+ `offline`) | 4 | 7 |
| 3 (+ `selecting`) | 8 | 11 |
| 4 (+ поиск) | 16 | 19 |

Вариантов `2^k`, где `k` — число независимых осей: не «растёт со временем», а
**удваивается на каждом требовании**. Четвёртая ось, которую ещё никто не
просил, стоит столько же, сколько три предыдущие вместе. Это и есть
экспоненциальный размер ДНФ — раскрытие скобок платится удвоением числа
слагаемых на каждый новый множитель.

### Чем сумма отличается здесь от флагов

Тремя независимыми битами описываются те же восемь сочетаний — плоская модель с
полями `isRefreshing`, `staleAt`, `selectedIds` выражает ровно столько же.
Кардинальность одинаковая; разница в том, что **сумма требует имени для каждой
точки произведения.** У флагов сочетание существует, но его не надо объявлять:
нет конструктора, нет ветки в `when`, нет имени.

И спросить надо, окупается ли имя. Имя окупается, когда что-то запрещает:
`Loading` и `Error` отдельными вариантами дают гарантию, что их не покажут
вместе. А все восемь сочетаний `refreshing × offline × selecting` легальны,
каждое встречается в жизни — значит имена даны множеству, из которого нечего
исключать.

### Чем это платится в коде

Дорого не объявление, а переходы. «Пользователь дёрнул pull-to-refresh» в
одноосной модели был бы одним полем; здесь это отображение вариантов на
варианты, выписанное руками:

```kotlin
fun OrdersState.startRefresh(): OrdersState = when (this) {
    is OrdersState.Content ->
        OrdersState.ContentRefreshing(orders)
    is OrdersState.ContentOffline ->
        OrdersState.ContentOfflineRefreshing(orders, staleAt)
    is OrdersState.ContentSelecting ->
        OrdersState.ContentSelectingRefreshing(orders, selectedIds)
    is OrdersState.ContentSelectingOffline ->
        OrdersState.ContentSelectingOfflineRefreshing(orders, selectedIds, staleAt)
    // ...и ещё семь ветвей на «уже обновляемся» и «контента нет»
}
```

Таких функций столько, сколько осей: включить выделение, выключить, пришёл
оффлайн, ушёл оффлайн. Каждая знает про все восемь вариантов и каждая ломается
при появлении девятого.

И главное: **компилятор проверяет здесь не то, что нужно.** Exhaustive `when`
проверяет, что покрыты все слагаемые суммы, — это работает. Но он ничего не
знает про множители, спрятанные в именах слагаемых: напиши для
`ContentSelectingOffline` переход в `ContentSelectingRefreshing` вместо
`ContentSelectingOfflineRefreshing` — всё сойдётся по типам и соберётся,
просто `staleAt` некуда будет передать, и плашка оффлайна исчезнет на время
обновления. Ошибка «потеряли ось при переходе» ловится глазами. Ровно тот
класс ошибок, от которого уходили в `sealed`, вернулся — как только осей стало
больше одной.

### Вывод пункта

**`sealed` окупается только там, где оси исключают друг друга. Иначе имена
даны зря** — и оплачены объявлением, перекладкой полей и багами на переходах.

## 2. Как отличить ось заранее

Теория говорит, что произведение нельзя раскрывать без нужды. Практический
вопрос — как отличить множитель от слагаемого до того, как в иерархии станет
одиннадцать имён. Тест в одну строку:

> **Могут ли оба быть верны одновременно — и это осмысленно?**
> Нет → слагаемые, одна сумма. Да → множители, независимые оси, им место в
> полях.

Слово «осмысленно» несёт вес: из алгебры оно не выводится. Кардинальность
домена — знание о продукте, а не о типах, и единственный способ его получить —
спросить, бывает ли так на экране. «Грузим и показываем ошибку» выразимо во
флагах, но в домене такого состояния нет — потому и сумма.

Три случая, на которых тест калибруется, потому что интуиция на них врёт.

**Случай 1. Режим выделения и пустой список.** Одновременно — нет, выделять
нечего. Но вывод не «это слагаемые одной суммы»: вывод в том, что `selecting`
— вообще **не ось всего экрана**, она существует только там, где есть
контент. Флаг `isSelecting` рядом с состоянием делает выразимым «грузим, и при
этом включён режим выделения» — то же невозможное состояние, этажом выше.
Значит ось живёт внутри `Content`, и там по тому же тесту она сумма
(«выключен» и «включён, ничего не выбрано» одновременно невозможны):

```kotlin
data class Content(
    val orders: List<Order>,
    val isRefreshing: Boolean,   // независимая ось → множитель → поле
    val staleAt: Long?,          // независимая ось → множитель → поле
    val selection: Selection,    // исключающая ось → сумма
) : OrdersState

sealed interface Selection {
    data object Off : Selection
    data class On(val selectedIds: Set<String>) : Selection
}
```

Одиннадцать вариантов свернулись в четыре, ни одного невозможного состояния не
добавилось. Заодно ушла двусмысленность `selectedIds = null` против
`emptySet()` — она была бы, сделай мы выделение просто nullable-полем: null
значил бы «режим выключен», пустое множество — «включён, ничего не выбрано», и
различие жило бы только в голове.

Обрати внимание на форму результата: сумма внутри произведения внутри суммы.
Алгебраические выражения не обязаны быть плоскими, и **каждый уровень
вложенности решается своим прогоном теста** — ось, бессмысленная над
`Loading`, не поднимается наверх, а остаётся внутри того слагаемого, где
осмысленна.

**Случай 2. Загрузка и контент.** Слово «грузим» покрывает две разные вещи:
грузим **впервые** — контента нет, показывать нечего, это исключает список и
потому слагаемое рядом с `Content`; грузим **ещё** (следующая страница) —
контент есть, спиннер поверх него, это множитель и потому поле
`isLoadingMore` внутри `Content`. Одно слово, две природы. Тест нельзя
прогонять по названиям полей — только по тому, что бывает на экране.

**Случай 3. Ошибка обновления при показанном списке.** Запрос упал, старый
список валиден. Прогон теста даёт третий ответ: это вообще не состояние, а
одноразовый эффект. В состоянии он переживёт поворот экрана и всплывёт
второй раз, потому что состояние по определению — то, что восстанавливается
при пересоздании UI. Но если продукт хочет не снекбар, а плашку «данные могли
устареть» до следующего успешного обновления — это состояние, и по тесту
множитель внутри `Content`. **Решает длительность**, а не слово «ошибка».

Отсюда тест из двух шагов: сначала — состояние ли это вообще; и только потом —
слагаемое или множитель.

### Вывод пункта

**`sealed` — только для исключающих ответов. Независимые оси — полями.**

## 3. Дублирование общих полей

Иерархия из пункта 1, восемь вариантов контента, в каждом свой `orders`.
Посмотрим, как она ведёт себя при обычном изменении: продукт просит поиск,
появляется `query: String`, нужная во всех вариантах контента, потому что
список отфильтрован в любом из них.

Восемь объявлений — и это только начало: каждое место, где вариант
конструируется, обязано новое поле передать. Четыре конструктора в
`startRefresh()`, столько же в каждой из остальных функций-переходов. Одно
продуктовое поле — порядка двадцати правок, и ни одна из них не про поиск, все
про перекладку.

Алгебраически это ровно то, что видно в формуле: `orders` и `query` — общие
множители всех восьми слагаемых. Раскрыв скобки, ты обязан выписать общий
множитель в каждое слагаемое, и дальше каждое изменение общей части умножается
на число слагаемых.

### Вынос наверх не помогает

Первый ход, который делает всякий, кто это увидел, — объявить общее поле один
раз, в самом `sealed interface`:

```kotlin
sealed interface OrdersState {
    val orders: List<Order>
    val query: String
}
```

Ломается сразу: `Loading` и `Empty` обязаны предъявить список, которого у них
нет. Поставить `emptyList()` по умолчанию — значит сделать выразимым «пусто, но
в нём пять заказов» и «грузим, а список уже есть». Кардинальность типа снова
больше, чем у домена, то есть несоответствие (а) — вернулись к тому, от чего
`sealed` и брали.

Тогда выносят не на самый верх, а на промежуточный этаж — только для
контентных вариантов:

```kotlin
sealed interface ContentLike : OrdersState {
    val orders: List<Order>
    val query: String
}
```

Из восьми объявлений после этого не исчезает **ни одного**: они становятся
`override val`. Плюс лишний этаж иерархии.

### Что вынос даёт и о чём говорит

Даёт он читателям: `state.orders` можно взять, не разбирая, какой из восьми
вариантов пришёл. Но посмотри, о чём эта просьба — читатель хочет, чтобы сумма
отдала поле, не спрашивая слагаемого, то есть повела себя как произведение.
`val` в интерфейсе это имитирует; объявления остаются, потому что сумма так не
умеет. Вынести общий множитель за скобки внутри ДНФ нельзя — вынос за скобки
и есть отказ от ДНФ.

Формально: **поле, которое есть во всех слагаемых, по определению не различает
слагаемые.** Значит оно не принадлежит оси, по которой разрезана сумма, — оно
множитель. А что делать с множителем, известно из пункта 2: держать полем.

Отсюда признак, работающий на ревью без всякой теории: **если в
`sealed interface` появился `val`, который реализуют все ветки — иерархия
разрезана по неверной оси.**

### Вывод пункта

**Общее поле у всех вариантов значит, что форма разрезана не по той оси.**
Желание вынести его наверх — не задача на рефакторинг иерархии, а диагноз
самой иерархии.

## 4. Цена возврата

Считаем, как любую миграцию: точки правки отдельно, решения — места, где
правка не механическая — отдельно. Всю стоимость определяет один вопрос:
меняется ли множество состояний.

**Не меняется.** Разросшаяся иерархия и гибрид изоморфны, отображение
один-в-один, все восемь:

| Было (слагаемое) | Стало (`Content` с полями) |
|---|---|
| `Content(o)` | `isRefreshing=false, staleAt=null, selection=Off` |
| `ContentRefreshing(o)` | `isRefreshing=true, staleAt=null, selection=Off` |
| `ContentOffline(o,s)` | `isRefreshing=false, staleAt=s, selection=Off` |
| `ContentOfflineRefreshing(o,s)` | `isRefreshing=true, staleAt=s, selection=Off` |
| `ContentSelecting(o,ids)` | `isRefreshing=false, staleAt=null, selection=On(ids)` |
| `ContentSelectingRefreshing(o,ids)` | `isRefreshing=true, staleAt=null, selection=On(ids)` |
| `ContentSelectingOffline(o,ids,s)` | `isRefreshing=false, staleAt=s, selection=On(ids)` |
| `ContentSelectingOfflineRefreshing(o,ids,s)` | `isRefreshing=true, staleAt=s, selection=On(ids)` |

Это несоответствие (б) из вступления, и у него есть точная цена: **решений
ноль.** Сравни с обратным направлением — перевод плоской модели с флагами в
`sealed` — там кардинальность падает, скажем с восьми сочетаний до четырёх
вариантов, и каждое исчезающее состояние требует продуктового ответа: «упало,
но старый список есть» и «обновляем поверх списка» осмысленны, а положить их в
`Error` и `Loading` некуда. Общее правило: **сужение множества состояний стоит
решений, смена формы при том же множестве — нет.**

Механика свёртки:

- восемь объявлений слагаемых → одно;
- четыре функции-перехода по восемь ветвей → по строке `copy()`;
- `when` по восьми именам в UI → одна ветка с чтением полей.

Работы меньше, чем в обратную сторону, потому что почти всё удаляется, а не
переписывается.

### Чем платишь

Одним, и это надо знать заранее. Было так:

```kotlin
when (state) {
    is ContentOffline -> {
        StaleBanner(state.staleAt)
        OrdersList(state.orders)
    }
    is Content -> OrdersList(state.orders)
    // забыл слагаемое — не соберётся
}
```

Стало так:

```kotlin
is Content -> {
    if (state.staleAt != null) StaleBanner(state.staleAt)
    OrdersList(state.orders)
}
```

Не написать этот `if` — всё соберётся, тесты не покраснеют, а плашка оффлайна
никогда не покажется. Причина в том же, о чём был пункт 1: компилятор умеет
требовать разбора **слагаемых** и не умеет требовать чтения **множителей**.
Сумма даёт проверку покрытия, произведение — нет.

Это зеркало бага из пункта 1: там форма ловила забытое поле, но пропускала
переход в соседнее слагаемое; здесь наоборот. Каждая форма закрывает один
класс ошибок и открыта для другого, и выбор между ними — не про «правильно»,
а про то, какой класс у тебя реально случается. Закрывать этот — тестом на
рендер; а если ось критична, отдать её вложенной сумме, как `Selection`: там
компилятор снова начинает требовать ветки.

### Вывод пункта

**Свернуть в гибрид дёшево — но компилятор перестаёт проверять чтение полей.**

## Границы этого правила

Теория даёт форму, но не отвечает на два вопроса, и врать про это не стоит.

**Кардинальность домена не выводится из кода.** Весь тест опирается на слово
«осмысленно», то есть на знание, бывает ли такое сочетание на экране. Продукт
меняет ответ: «обновление поверх контента» год назад не существовало, и форма
была верной. Правильная форма — не свойство типа, а соответствие типа домену
на сегодня, и она устаревает вместе с требованиями.

**Не всякое невозможное состояние стоит запрещать типом.** Есть аргумент
против безоглядного «сделай невозможное невыразимым»: иногда дешевле
разрешить невалидное состояние и обработать его в логике, чем тащить его
запрет через всю форму. Проверка простая — во что обходится запрет: если
гарантия стоит одного слагаемого, она почти бесплатна; если ради неё
раскрываются скобки на три оси, она стоит одиннадцати имён, и это уже
дороже бага, от которого она защищает.

## Короткий ответ на вопрос

`sealed`-иерархия становится долгом в момент, когда в неё попадает **вторая
независимая ось**. Дальше всё предсказуемо: варианты удваиваются на каждой
новой оси, общие поля дублируются по слагаемым, переходы между слагаемыми
пишутся руками, а exhaustive `when` продолжает проверять покрытие ветвей и
перестаёт ловить главную ошибку — потерянную ось.

Диагностика — два признака, оба видны на ревью:

- в именах вариантов появились сочетания (`ContentOfflineRefreshing`);
- в `sealed interface` появился `val`, который реализуют все ветки.

Лечение — вынести общий множитель за скобки: внешнее произведение из общих и
независимых полей, вложенная сумма на каждой действительно исключающей оси.
Стоит это ноль продуктовых решений, потому что множество состояний не
меняется, и оплачивается одним: чтение полей компилятор больше не требует.
