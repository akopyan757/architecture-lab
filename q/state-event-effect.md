# state / event / one-time effect: почему effect не живёт в state

Issue: [#11](https://github.com/akopyan757/architecture-lab/issues/11) · раздел: [1. Состояние и поток данных](../architecture-map.md)

**Доказано:** нечем — рассуждение и модельный код в тексте, отдельного стенда
нет. Сценарии поворота и двух сообщений подряд разобраны по шагам, но сняты с
головы, а не с устройства.

## Три вещи по одному признаку

На экране ходят сообщения трёх видов, и различаются они не типом данных, а
тем, **что происходит, если сообщение прочитать дважды.**

**State** — «как выглядит экран сейчас». Прочитать его можно сколько угодно
раз, результат один: `isLoading = true` отрисуется одинаково и в первый раз, и
после поворота, и после возврата из бэкстека. Чтение state идемпотентно, и
именно на это опирается всё, что его читает — рекомпозиция, восстановление
после поворота, повторная подписка. Они читают когда хотят и сколько хотят,
не спрашивая разрешения.

**Event** — факт о пользователе, идёт вверх: «нажал», «ввёл», «свайпнул». Про
event уже был разбор [#9](https://github.com/akopyan757/architecture-lab/issues/9) ([`q/udf.md`](udf.md)): вверх идёт намерение, а не
готовое значение. Здесь он нужен только как третий угол треугольника — чтобы
было видно, что effect не является ни одним из двух других.

**One-time effect** — команда «сделай один раз», идёт вниз: «покажи snackbar»,
«открой экран», «вибрируй». Его нельзя прочитать дважды без последствий:
второе чтение — это второй snackbar, второй переход, вторая вибрация. Effect
не описывает экран, он описывает **переход**, который должен случиться ровно
один раз и после этого исчезнуть.

Разница между state и effect — в одной строке:

```kotlin
data class State(val isSaving: Boolean)      // прочитал дважды → один экран
data class State(val showSaved: Boolean)     // прочитал дважды → два snackbar
```

Синтаксически это одно и то же поле. Семантически первое — данные, второе —
команда, притворяющаяся данными. Весь дальнейший разбор — про то, что
случается с командой, когда её кладут туда, откуда читают многократно.

Отсюда формулировка вопроса: **effect не живёт в state, потому что state
читают, а effect выполняют.** Читать можно сколько угодно, выполнять — нет.

## Что ломается

Самый частый случай: после сохранения нужно показать snackbar «Сохранено».
Кладём в state поле:

```kotlin
data class State(val items: List<Item>, val message: String? = null)

fun onSaveClicked() = viewModelScope.launch {
    repo.save(draft)
    _state.update { it.copy(message = "Сохранено") }
}
```

UI подписан на state и при `message != null` показывает snackbar. Работает
ровно до первого события, которое заставит UI прочитать state ещё раз.

**Поломка первая — повтор.** Пользователь сохранил, увидел snackbar, повернул
экран:

```
шаг  кто           что произошло                          state.message   на экране
1    пользователь  нажал «сохранить»                      null            —
2    ViewModel     save() завершился, update(message)     "Сохранено"     snackbar #1
3    пользователь  повернул телефон                       "Сохранено"     UI уничтожен
4    новый UI      подписался, прочитал текущее значение  "Сохранено"     snackbar #2
```

То же самое при возврате с другого экрана, при `onStart` после сворачивания,
при любой рекомпозиции, где snackbar завязан на поле напрямую. Причина не в
Compose и не в `StateFlow`: они делают ровно то, для чего созданы — отдают
последнее значение каждому новому читателю. Проблема в том, что в это
значение попала команда.

**Поломка вторая — склейка.** Сохранение упало дважды подряд с разными
ошибками, или пользователь дважды быстро нажал «удалить». Между двумя
чтениями UI state обновился два раза:

```
шаг  кто        что произошло                  state.message    на экране
1    ViewModel  update("Ошибка сети")          "Ошибка сети"    UI ещё не прочитал
2    ViewModel  update("Нет места")            "Нет места"      перезаписало шаг 1
3    UI         прочитал                       "Нет места"      один snackbar
```

State по природе хранит последнее значение, а не историю. Для данных это
правильно: экрану не нужны все промежуточные `isLoading`. Для команд это
потеря: первая команда исчезла, никто её не выполнил.

**Почему это одна и та же поломка.** В обоих случаях state сделал то, что
должен: отдал текущее значение по запросу. Повтор — потому что читателей стало
больше, чем один. Склейка — потому что записей стало больше, чем чтений.
Effect требует ровно `1 запись → 1 выполнение`, а state ничего такого не
гарантирует, он гарантирует только «последнее значение доступно всегда». Это
разные контракты, и попытка натянуть один на другой даёт либо лишние
выполнения, либо пропущенные.

И ещё один способ увидеть разницу: `isLoading = true` после поворота **всё ещё
правда** — загрузка идёт, экран обязан это показать. `message = "Сохранено"`
после поворота **уже не правда** — сохранение случилось один раз в прошлом,
уведомление показано, факта «сейчас нужно показать snackbar» больше нет. Поле
хранит устаревшую команду и выдаёт её за текущее состояние. Отсюда
практический тест: **если значение может протухнуть само по себе, без нового
события, это не state.**

## Два выхода и их цена

Оба честные, у обоих есть за что платить.

### Выход А: оставить в state, но сделать состоянием

Раз проблема в том, что команда протухает, а state не знает об этом, добавляем
явный сигнал «выполнено»:

```kotlin
data class State(val items: List<Item>, val message: String? = null)

fun onMessageShown() = _state.update { it.copy(message = null) }
```

UI показывает snackbar и тут же вызывает `onMessageShown()`. После поворота
`message = null`, повтора нет. Поле перестало быть командой: «есть непоказанное
сообщение» — это факт про экран, и он честно сбрасывается, когда перестаёт
быть правдой. Это позиция официального гайда Android по UI events: событие из
ViewModel должно приводить к обновлению state, а не пролетать мимо него.

Цена:

- **Ручной цикл сброса.** Каждый effect тянет за собой пару «поле + метод
  потребления». Забыл вызвать — получил повтор. Компилятор не помогает.
- **Гонка сброса.** Между показом snackbar и `onMessageShown()` есть окно.
  Если в него прилетит второе сообщение, `onMessageShown()` затрёт его: UI
  потребил первое, а обнулил второе. Склейка никуда не делась, просто стала
  реже.
- **Один слот.** Поле `String?` держит одно сообщение. Нужна очередь — храни
  `List<Message>` и потребляй по id. Это уже маленькая подсистема внутри
  state.

### Выход Б: отдельный канал

Команда идёт не через state, а рядом:

```kotlin
private val _effects = Channel<Effect>(Channel.BUFFERED)
val effects = _effects.receiveAsFlow()

fun onSaveClicked() = viewModelScope.launch {
    repo.save(draft)
    _effects.send(Effect.ShowMessage("Сохранено"))
}
```

`Channel` отдаёт каждый элемент ровно одному получателю ровно один раз.
Повтора при повороте нет: значение уже забрано, новому подписчику отдавать
нечего. Склейки нет: буфер хранит оба сообщения, и они уйдут по очереди.
Контракт `1 запись → 1 выполнение` соблюдается самим примитивом, а не
дисциплиной вызова `onShown()`.

Цена:

- **Потеря без подписчика.** Если UI не подписан в момент отправки, в
  небуферном варианте `send` подвиснет, в буферном сообщение полежит, а с
  `SharedFlow(replay = 0)` пропадёт совсем. Экран в бэкстеке, приложение
  свёрнуто, эффект пришёл после `onStop` — вопрос «где он теперь» надо решать
  явно.
- **Не переживает смерть процесса.** State можно сохранить в
  `SavedStateHandle`, канал — нет. Если эффект важен настолько, что его нельзя
  потерять, он должен был быть состоянием.
- **Второй поток данных из ViewModel.** Тесты, логи, отладка: у экрана теперь
  два выхода вместо одного, и порядок между ними не гарантирован. Snackbar
  может прийти раньше, чем state, в котором список уже обновился.

**Что здесь важно увидеть.** Выход А не превращает effect в state
волшебством. Он берёт то, что в эффекте было состоянием («есть непоказанное
сообщение»), и хранит это. Выход Б берёт то, что в эффекте было командой, и
доставляет ровно один раз. Спор Manuel Vivo (за state) и Gabor Varadi (за
канал) ровно об этом: первый показывает, что почти всё можно переформулировать
как факт про экран, второй — что цена переформулировки (цикл сброса, гонка,
слот) иногда выше цены канала.

## Критерий выбора

Навигация «после логина открыть главный экран» — хороший тест на оба выхода.
Пользователь повернул телефон ровно в момент, когда логин завершился.

**Канал.** ViewModel отправила `Effect.NavigateHome`. В этот же момент экран
пересоздаётся: старый подписчик отменён, новый ещё не подписался. С
`SharedFlow(replay = 0)` эффект ушёл в пустоту. С буферным `Channel` он
полежит и дойдёт до нового подписчика, но это уже зависит от выбранного
примитива и от того, когда именно случилась отписка. А если процесс убит в
фоне, эффект пропал в любом варианте: пользователь залогинен, а стоит на экране
логина.

**Состояние.** Не «открой главный экран», а «пользователь авторизован»:

```kotlin
data class State(val isAuthorized: Boolean)
```

Навигация становится производной от факта: `isAuthorized == true` — показываем
главный. Поворот безразличен: новый подписчик прочитает `true` и покажет то,
что надо. Смерть процесса безразлична: факт восстанавливается из сессии.
Повтора нет, потому что «показать главный экран» при уже показанном главном
ничего не делает — это state, чтение идемпотентно.

Переформулировка убрала саму проблему one-time. Команда «перейди» была
одноразовой, факт «авторизован» одноразовым не бывает: он просто истинен или
ложен.

Отсюда единственный вопрос, который надо задать каждому эффекту: **можно ли
это переформулировать как факт про экран так, чтобы повторное чтение не
требовало ничего делать?**

| Эффект | Попытка переформулировать | Итог |
|---|---|---|
| «Открой главный» | «авторизован» | state |
| «Покажи ошибку загрузки» | «загрузка завершилась ошибкой X», живёт до следующей загрузки | state (вопрос #16) |
| «Покажи snackbar Сохранено» | «есть непоказанное подтверждение» + сброс | пограничный: А или Б |
| «Вибрируй», «проиграй звук», «открой share sheet» | факта про экран нет | effect, канал |

Правило целиком: сначала пробуй сделать состоянием. Если получилось без флага
потребления — это и было состояние, просто названное как команда. Если флаг
потребления понадобился — ты стоишь перед честным выбором А или Б, и решает
то, что дороже потерять: лишний показ или пропущенный. Если факта не нашлось
вовсе — это effect, и класть его в state значит выдавать команду за данные.

## Итог

State читают, effect выполняют. Всё, что можно читать многократно без
последствий, живёт в state. Всё остальное сначала пытаются переформулировать в
такое — и чаще всего получается, потому что за командой обычно стоит факт.
Только то, что не переформулировалось, идёт отдельным каналом с его ценой: без
подписчика теряется, смерть процесса не переживает. Ни один из выходов не
бесплатный, но оба лучше третьего — команды в state, которая выполняется
столько раз, сколько раз её прочли.
