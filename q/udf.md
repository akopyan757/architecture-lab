# UDF: что ломается при двунаправленном потоке

Issue: [#9](https://github.com/akopyan757/architecture-lab/issues/9) · раздел: [1. Состояние и поток данных](../architecture-map.md)

**Доказано:** код в [`q/udf/`](udf/) — одно и то же поле ввода с ограничением
по длине в двустороннем и однонаправленном варианте, плюс
[`trace.md`](udf/trace.md): эхо-цикл и два расхождения, записанные по шагам и
воспроизводимые руками. Прогона на устройстве нет, трассировки сняты с
модельного кода — это оговорено там же.

## Что называется двунаправленным потоком

Признак один: **значение может быть изменено с двух сторон, и обе стороны
считают себя правыми.**

Это не то же самое, что «данные ходят туда-сюда». Туда-сюда они ходят всегда:
состояние вниз, события вверх — это и есть UDF (unidirectional data flow).
Двунаправленность начинается там, где вверх идёт не событие, а готовое
значение, которое принимающая сторона обязана принять как факт.

```kotlin
onTextChange(TextChanged(newValue))  // вверх ушло намерение: владелец решит
state.text = newValue                // вверх ушло решение: владельцу сообщили
```

Синтаксически разница почти нулевая. Разница в том, есть ли у владельца право
сказать «нет, будет иначе». Во втором случае права нет: значение уже изменилось
на той стороне, модель лишь догоняет.

Про направления, чтобы не путаться: **вниз течёт значение, вверх — факт о
пользователе.** «Вот как выглядит экран» ↓ / «нажал, ввёл, свайпнул» ↑.

Это не то же, что SSOT (разбор [#8](https://github.com/akopyan757/architecture-lab/issues/8), [`q/ssot.md`](ssot.md)): SSOT отвечает на вопрос
«сколько мест хранит значение», UDF — «в какую сторону идут изменения».
У значения может быть единственный владелец, и оно всё равно правится с двух
сторон.

## Что именно ломается

Возьмём поле ввода с одним безобидным правилом — не длиннее 20 символов — и
двусторонним биндингом ([`two_way.kt`](udf/two_way.kt)).

```kotlin
text.onChange { editText.setText(it) }            // вниз
editText.doAfterTextChanged { setText(it) }       // вверх: значение, не событие
fun setText(value: String) = text.set(value.take(20))
```

**Симптом первый — эхо.** Пользователь печатает одну букву:

```
1. ввёл "a"                → editText = "a"
2. doAfterTextChanged("a") → text.set("a")
3. onChange("a")           → editText.setText("a")
4. doAfterTextChanged("a") → text.set("a")
   ... условия выхода нет
```

Начиная с шага 2 значение не меняется, но цикл этого не знает: запись с обеих
сторон безусловная. Останавливает его не логика, а страж.

**И вот здесь главное: страж — не починка, а глушение симптома.** Он гасит
цикл, но вместе с ним гасит и легитимное обновление. Проверяется на трёх
шагах — в поле 20 символов, курсор в позиции 5, пользователь вводит 21-й.

Страж по равенству (`if (editText.text != value) setText(value)`):

```
1. ввод "X" в позицию 5    → editText: 21 символ,  модель: 20
2. setText(take(20))       → модель обрезала, экран нет — разошлись
3. страж: 21 != 20         → setText(20) → курсор прыгает в конец
```

Значения сошлись, курсор — нет: View получила строку, которую считает новой, и
поставила каретку в конец. Пользователь правил середину, а печатать
продолжает в хвосте. Плюс между шагами 2 и 3 есть момент, когда на экране 21
символ, а в модели 20, и на нём выполняется всё, что читает поле.

Страж по флагу (`if (isUpdating) return`) ломается хуже:

```
1. ввод "X" в позицию 5    → editText: 21 символ
2. isUpdating = true, setText(take(20)) → модель: 20
3. onChange: isUpdating    → return, связь вниз подавлена целиком
```

Расхождение остаётся навсегда: модель хранит 20 символов, экран показывает 21,
форма уйдёт с тем значением, которого пользователь не видел. Флаг ставился
ради выхода из цикла и заодно выключил единственный путь, которым владелец мог
поправить экран.

Полные трассировки — в [`trace.md`](udf/trace.md).

Обобщая, ломается вот что:

- на вопрос «кто сейчас владелец значения» нет ответа;
- появляется эхо: модель обновила виджет, виджет сообщил об изменении, модель
  обновилась снова;
- состояние нельзя восстановить, зная только последовательность действий
  пользователя — нужен ещё порядок колбэков;
- результат зависит от этого порядка, а не от порядка строк в коде.

Это не «становится сложнее». Это четыре называемых симптома, и первый из них —
корневой: пока стрелка одна, владелец известен по построению.

## Где двунаправленность заводится сама

Главный практический пункт: почти никто не выбирает двусторонний биндинг
сознательно. Он приезжает вместе с платформенным виджетом.

**Правило: у любого компонента, который умеет реагировать на пользователя без
вашего кода, есть собственная копия состояния.**

| Компонент | Своё состояние | Кто меняет мимо владельца |
|---|---|---|
| Поле ввода | текст, курсор, IME-композиция | клавиатура, автозамена, вставка |
| Скролл, LazyList | позиция, offset | палец, fling, restore при повороте |
| Чекбокс, Switch | checked | тап, до вашего колбэка |
| Анимация | значение между кадрами | часы кадров |
| WebView, MapView, плеер | всё | внутренний движок |

Отсюда неочевидное: `TextField(value = state.text, onValueChange = { ... })` —
UDF по форме, но двунаправленность внутри. Наверху всё честно: значение пришло
сверху, наверх ушёл колбэк. Но у виджета остаётся буфер текста и позиция
курсора, которых владелец не видит. Пользователь правит их напрямую, владелец
узнаёт постфактум — ровно «изменено с двух сторон».

Скролл — тот же механизм, только заметнее:

```kotlin
LaunchedEffect(state.selectedIndex) { listState.animateScrollToItem(state.selectedIndex) }
LaunchedEffect(listState.firstVisibleItemIndex) { vm.onScrolled(listState.firstVisibleItemIndex) }
```

Это эхо из предыдущего раздела, только через две корутины: скролл пальцем →
`onScrolled` → изменился `selectedIndex` → `animateScrollToItem` → снова
`onScrolled`. Список дёргается и не даёт себя прокрутить.

Что с этим делают — не «запрещают», а выбирают одно из трёх:

1. **Отдать владение виджету.** Позиция живёт в `rememberLazyListState()`,
   владелец её не знает. Работает, пока состояние никому не нужно снаружи.
2. **Забрать владение целиком, вместе с курсором.** Не `String`, а
   `TextFieldValue`: сверху приходит и текст, и селекция, владелец обрезает
   строку и сам говорит, куда встанет каретка ([`udf.kt`](udf/udf.kt)).
   Расхождения нет, потому что виджету нечего иметь своего.
3. **Разделить: буфер внизу, факт наверху.** Виджет держит сырой ввод, наверх
   идёт осмысленное событие — по debounce, по фокусу, по кнопке. Так живут
   поиск и формы.

Общее у трёх вариантов одно: **владелец ровно один, и это выбрано явно.**
Ломается не когда состояние внизу, а когда на вопрос «чьё оно» нет ответа.

## Чем платят за UDF

Двусторонний биндинг — не ошибка, а сделка: предсказуемость в обмен на
короткий путь. Иногда путь важнее, и разбор без этого пункта превращается в
проповедь ([`cost.kt`](udf/cost.kt)).

**Лишний круг.** Каждое нажатие клавиши проходит маршрут
`клавиша → событие → reducer → новый state → emit → рекомпозиция → виджет`.
Пока там `state.copy(text = it)`, это микросекунды. Но маршрут утяжеляется
случайно:

```kotlin
state.copy(text = q, filtered = items.filter { it.name.contains(q) })  // 5000 элементов
```

Теперь фильтрация стоит между клавишей и буквой, плюс `emit` через главный
диспетчер — это минимум следующий кадр. Символы отстают от пальца, видно
глазом. Причина не в UDF, а в том, что круг через владельца сделал синхронным
то, что раньше было локальным. Лечится тем же разделением: наверх по-прежнему
идёт каждое нажатие, тяжёлое вычисление снято с пути ввода.

**Церемония на пустом месте.** Поле в state, событие, ветка в reducer, строка
в UI — четыре точки правки ради раскрытого меню, которое не переживёт поворот
и никого не волнует. Проверка — три вопроса:

1. Читает ли это состояние кто-то, кроме самого виджета?
2. Должно ли оно пережить смерть виджета — поворот, бэкстек, process death?
3. Влияет ли оно на что-то за пределами отрисовки — запрос, навигацию,
   аналитику?

Все три «нет» — оставляйте внизу, это не нарушение UDF. Хотя бы одно «да» —
поднимайте, иначе получите расхождение из предыдущего раздела.

**Разрыв причины и следствия.** В двустороннем биндинге место записи видно в
стектрейсе. В UDF между событием и изменением стоит reducer, а стектрейс
обрывается на `emit`. Отладка идёт по логу событий — на дистанции это лучше,
последовательность воспроизводима, но требует, чтобы лог существовал. Без него
UDF отлаживается хуже, чем биндинг.

## Итог

UDF нужен не ради красоты схемы, а ради того, чтобы на вопрос «кто владеет
значением» всегда был ответ. Двунаправленность почти никогда не выбирают —
её приносит платформенный виджет со своей копией состояния, и обнаруживается
она не в архитектурном обсуждении, а прыгающим курсором и полем, которое
отправляет не то, что показывает. Платите вы лишним кругом и церемонией, и
платить стоит ровно там, где значение нужно кому-то снаружи виджета.
